# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

The solution `src/MyApplication/MyApplication.sln` has five projects: `MyApplication.Domain`, `MyApplication.Application`, `MyApplication.Infrastructure`, `MyApplication.Api` (Presentation) — a full Clean Architecture layering — plus `MyApplication.Tests` (xUnit, not shipped). Two use cases exist: `Notes`, a real CRUD feature spanning all four layers, backed by PostgreSQL via EF Core, and `Auth` — Google-login-based JWT authentication (own access + refresh tokens, Google itself only validates the initial ID token via `IGoogleIdTokenValidator`), which also makes `Notes` per-user-private (`Note.UserId`, no FK across the two features' DbContexts — separate bounded contexts, see `MyApplication.Infrastructure/Auth/` vs `MyApplication.Infrastructure/Notes/`). A brand-new user also gets one **welcome note** ("Добро пожаловать") on their first login — `AuthService` calls the `IUserRegistrationHandler` port, `Notes` implements it (`WelcomeNoteRegistrationHandler`); the two writes are deliberately **not atomic**, see the `Application` entry below and `docs/docs/auth/business-rules.md`. `DomainExceptionHandler` maps exceptions to 400/401/403/409 by type (see its own entry below), not a flat 400 like before. `Notes` also carries optimistic concurrency: `Note.Version` (int, `Note.InitialVersion` = 1, +1 per `Update`) is echoed back by the client on every `PUT`, and a mismatch is a 409 (`NoteConflictException`) instead of a silent overwrite — that's what keeps the same note open in two tabs from losing edits; see `docs/docs/notes/business-rules.md`. `Notes` also has **search** (`GET /Notes/search`, the search box in the UI header): matching and relevance ranking are done by Postgres itself via the `pg_trgm` extension (trigram similarity — that's what finds a note despite a typo in the query), while the snippet around the match and the highlighted ranges are built in the Application layer (`SearchSnippetBuilder`); see `docs/docs/notes/business-rules.md` («Поиск»). (An earlier `WeatherForecast` placeholder, inherited from the ASP.NET Core template, was deleted once it had no test coverage and no real business logic — don't recreate that pattern for new features.) A second Presentation surface, `src/MyApplication.Web.UI/` (React SPA), lives alongside the solution — a separate Node/npm project, not a `.sln` project — see its own entry in Structure below.

## Structure

- `README.md` — run instructions (local + Docker + Docker Compose/ELK + tracing + docs site).
- `.claude/skills/` — skills available to Claude Code in this repo. Currently one: `android-development`, a third-party skill installed on request (dpconde/claude-android-skill — NowInAndroid-style Android guidance: Compose patterns, module layout, Gradle setup, plus a feature generator script). **It is background material, not policy: this file, `docs/docs/` and the decisions already made in the code outrank it.** It assumes a large multi-module app (Hilt, `feature:*:api`/`impl`, `build-logic` convention plugins, offline-first Room as the source of truth) and pins compileSdk 34 / Kotlin 1.9.22 / the `org.jetbrains.kotlin.android` plugin — the last of which AGP 9 rejects outright as a build error. Borrow idioms from it; don't restructure existing code to match it.
- `docs/` — a separate [Docusaurus](https://docusaurus.io/) site documenting the application's **business logic** (use cases/business rules/API contracts), independent of this repo's technical README/CLAUDE.md. Content lives under `docs/docs/`, one folder per use case (currently just `notes/`, the CRUD notes feature), with `_category_.json` files controlling the sidebar tree — `sidebars.js` auto-generates the sidebar from that folder structure, so **adding a new use case is just adding a new folder** there. Has its own `package.json`/`node_modules`/`.npmrc` (Node/npm project, unrelated to the .NET solution) — `npm install --global=false && npm start` from `docs/`. `docs/.npmrc` forces local (non-global) installs — needed in some environments where a user-level npm config defaults `npm install` to global/misresolved locations; keep it even if your own environment doesn't need it. When real business logic is added to `MyApplication.Application`, add/update the corresponding page(s) under `docs/docs/` in the same change. **This also runs in reverse: treat `docs/docs/` as the spec.** If a change to `docs/docs/` describes new or different application behavior than what `MyApplication.Application` currently implements (not just wording/formatting edits), don't just accept the doc edit — point out the mismatch and propose the corresponding code change, and only implement it once the user confirms. Published automatically to GitHub Pages at `https://rualert.github.io/my-application/` by `.github/workflows/deploy-docs.yml` on every push to `master` touching `docs/**` — keep `docusaurus.config.js`'s `url`/`baseUrl` (`https://rualert.github.io` / `/my-application/`) in sync if the repo or org is ever renamed.
- `load-tests/` — [k6](https://k6.io/) load-test scenarios, plain JS, no `package.json`/build step, run via the `grafana/k6` Docker image or a local `k6` binary (not part of `MyApplication.Tests`, not restored/built by `dotnet`). One file per scenario under `scenarios/` (currently `notes-list.js` for `GET /Notes`, `notes-get-by-id.js` for `GET /Notes/{id}`, `notes-create.js` for `POST /Notes` — that one's own request load *is* the write being measured, `SEED_COUNT` there only sets the starting table size, not the thing under test), shared config in `config.js`, shared seeding helper in `lib/seed.js`, shared login helper in `lib/auth.js`. `/Notes` is JWT-protected and per-user-private (see `Auth`, below) — every scenario's `setup()` logs in once via `lib/auth.js`'s `loginLoadTestUser()` (a real `POST /Auth/google`) and attaches the resulting access token as `Authorization: Bearer` to every request (seeding and the load itself), so the whole run acts as one fixed load-test user (that first login also creates the user's welcome note, so its table holds one note more than `SEED_COUNT` — negligible next to thousands, but don't be surprised by an off-by-one). Real Google isn't reachable/needed just to measure RPS, so this only works against the isolated stand (`ci/docker-compose.load-tests-db.yml`, `ASPNETCORE_ENVIRONMENT=LoadTest`, see below) — that environment name makes `Program.cs` swap in `LoadTestGoogleIdTokenValidator` instead of the real Google validator (same trick as `FakeGoogleIdTokenValidator` in `SmokeTests`). One login per run, no refresh — `Jwt:AccessTokenLifetimeMinutes` is raised for that isolated stand accordingly (see below). Each scenario uses the `ramping-arrival-rate` executor to step the target RPS up (stages configurable via `STAGE_TARGETS`/`STAGE_DURATION` env vars) against `thresholds` (`http_req_failed`, `http_req_duration` p99) — the goal is finding the highest RPS stage that still meets both, not a pass/fail CI gate. Points `BASE_URL` at a real deployed instance, not `WebApplicationFactory`, since in-process hosting doesn't reflect real network/connection-pool behavior under load — by default that's the isolated instance from `ci/docker-compose.load-tests-db.yml` (see below and the `scripts/` entry), not the regular dev app.
  - `lib/seed.js` — seeds `SEED_COUNT` notes via `http.batch()` in batches of `BATCH_SIZE` (50), not one request at a time. **A large `SEED_COUNT` (thousands) with sequential seeding blows past k6's default `setupTimeout` (60s)**, aborting the whole run with `setup() execution timed out` before any load is generated — looks from the outside like the `SEED_COUNT` parameter was silently ignored. Batching plus each scenario's `options.setupTimeout: '5m'` (defense-in-depth on top of batching) fixes that. If `SEED_COUNT` ever needs to go well beyond ~10k, re-check the batch math rather than assuming this is still headroom.
  - `lib/stageThresholds.js` — tags every request with its current stage's target RPS (`stage_rps`, computed from `k6/execution`'s `currentTestRunDuration` — k6 exposes no public API to ask the `ramping-arrival-rate` executor which stage it's on) and duplicates each scenario's `thresholds` as per-stage submetrics (`http_req_duration{stage_rps:400}`, etc), not just the whole-run aggregate.
  - `lib/maxRpsSummary.js` — each scenario's `handleSummary()` calls into this to scan those per-stage submetric thresholds and print `Maximum RPS satisfying thresholds: <n>` straight to the console (the highest stage where every threshold still passed) — no need to eyeball Grafana just to find that number. Defining `handleSummary()` stops k6's automatic summary print, so this reconstructs it via jslib's `textSummary` (fetched from `jslib.k6.io` at run time — needs outbound network from the k6 container/binary, same as any other remote k6 import). Also appends a markdown table row (date, max RPS, the scenario's `thresholds` rules, `SEED_COUNT`) to `results/<scenario>.md` — see below; `thresholds`/`SEED_COUNT` ride along because both can change between runs and the RPS number alone is meaningless without knowing which pair it was measured under. **Real k6 quirk, not a bug: `open()` only works during the init stage** (script top-level, before any iteration/VU runs) — calling it from inside `handleSummary()` itself throws `"open function is only available in the init stage"`, since by then the run has finished. That's why each scenario reads its results-file history (`readResultsHistory()`) at its own top level and only passes the already-read string into `summarizeMaxRps()`/`handleSummary()` — don't move that call into `handleSummary()` to "simplify" it, it'll break. Also note `open()` and the `handleSummary()` output-object keys resolve relative paths *differently*: `open()` is relative to the calling script file (`scenarios/`, hence the `../results/...` prefix used there), while output-object keys are relative to the k6 process's cwd (`load-tests/`, hence the bare `results/...` used for the written path) — confirmed empirically, not documented clearly by k6 itself.
  - `results/notes-list.md`, `results/notes-get-by-id.md`, `results/notes-create.md` — a markdown table (`| Дата | Max RPS | Thresholds | Seed count |`), one row per run, appended (not overwritten) by the `handleSummary()` mechanism above. A history in git, independent of InfluxDB/Grafana retention.
  - See `load-tests/README.md` for exact run commands. Results are also viewed in Grafana for the full time-series picture — see the `ci/docker-compose.load-tests.yml` entry below.
  - `scripts/` — PowerShell wrappers around the `docker run ... grafana/k6 run ...` invocation, for convenience on this (Windows) dev machine. `Invoke-K6Scenario.ps1` does the actual `docker run` (takes `-ScenarioFile`, `-AppPort`, `-BaseUrl`, `-Network`, `-InfluxUrl`, `-SeedCount`, `-StageDuration`, `-StageTargets`, `-KeepDb`); `Invoke-NotesListScenario.ps1`/`Invoke-NotesGetByIdScenario.ps1`/`Invoke-NotesCreateScenario.ps1` are thin per-scenario wrappers that forward `$PSBoundParameters` to it plus their own `-ScenarioFile`. A new scenario needs its own such wrapper (copy an existing one, swap the `-ScenarioFile` literal and the `.SYNOPSIS`/`.EXAMPLE` text — nothing else differs). Any new param added to `Invoke-K6Scenario.ps1` must be copy-pasted into every wrapper's own `param()` block too, or passing it to a wrapper fails with "parameter not found" — `$PSBoundParameters` only forwards what the *wrapper itself* declares. **Gotcha already hit once: declare RPS-list parameters as `[string[]]` (joined with `,` before use), not `[string]`** — PowerShell parses an unquoted comma-separated value like `-StageTargets 10,20` into an array at the call site before binding, so a `[string]` parameter fails to bind for that (very natural, unquoted) calling style. Also handles k6's exit code **99** specially — that means "a threshold was breached," the expected/normal outcome of these scenarios (not a tooling failure), so it's reported via `Write-Warning` instead of a terminating `throw`; any other non-zero code still throws. **`Invoke-K6Scenario.ps1` also owns the lifecycle of `ci/docker-compose.load-tests-db.yml`** (see below): brings it up before the k6 run, polls `http://localhost:$AppPort/Notes` from the host until it responds with 2xx or 401 (no health endpoint/curl in the image for a Docker-level healthcheck, so this is done from PowerShell instead; 401 counts as ready too since `/Notes` is `[Authorize]`-protected and the probe has no token yet — a 401 still proves the app booted, migrations ran, and the auth pipeline is live), then tears it down (`down -v`) in a `finally` block regardless of how the k6 run went — unless `-KeepDb` is passed. Default `-BaseUrl` points at this isolated instance (`http://host.docker.internal:$AppPort`, `$AppPort` defaults to 8081), not the regular dev app on 8080.

Triggers on push to `master` (paths `docs/**`) or manually (`workflow_dispatch`). Requires the repo's **Settings → Pages → Source** to be set to "GitHub Actions" (one-time, done outside the workflow itself).

The job id (`backend`/`web-ui`) *is* the check name there, so renaming a job means re-selecting it in the protection rule (a rule still requiring the old name would wait forever for a check that no longer exists).
- `.github/workflows/android.yml` / `.github/workflows/android-release.yml` — the two Android workflows, deliberately separate. `android.yml` runs `testDebugUnitTest` + `assembleDebug` on PRs/pushes touching `src/MyApplication.Android/**` and uploads the debug APK as a build artifact — a build check, **not** something to hand out: the runner generates a fresh debug keystore per run, so its SHA-1 isn't the one registered in Google Cloud and Google login in that APK fails. `android-release.yml` is the distribution path: triggered by pushing an `android-v*` tag (the prefix is required — one repo holds the API, the web UI and this client, so a bare `v*` wouldn't say what is being released), it runs the tests, builds `assembleRelease` signed with the release keystore restored from `ANDROID_KEYSTORE_BASE64` (+ `ANDROID_KEYSTORE_PASSWORD`/`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD`, alongside the existing `GOOGLE_CLIENT_ID`) and attaches `MyNotesApp-<version>.apk` to a GitHub Release via `gh release create` (`permissions: contents: write`) — a release asset downloads without a GitHub login and unzipped, unlike an artifact. `versionName` comes from the tag minus its `android-v` prefix, `versionCode` from `github.run_number` (monotonic — Android refuses to install over a higher one); both arrive as `-PmyNotesApp.*` build settings, like every other Android build setting. The release keystore's SHA-1 must be registered as an Android OAuth client in the `mynotesapp-509010` Google Cloud project, separately from the debug key — commands and the one-time setup are in `src/MyApplication.Android/README.md` («Выпуск APK»). `assembleRelease` without those four settings still succeeds but yields `app-release-unsigned.apk`, which won't install.
- `ci/` — every Dockerfile / Docker Compose file lives here (moved out of the repo root once there were enough of them to be clutter — explicit user request). All commands below are run **from the repo root**, not from inside `ci/` (`docker compose -f ci/docker-compose.X.yml ...`, `docker build -f ci/Dockerfile ...`) — this matters because compose resolves a file's relative paths (bind mounts, build context) against the compose file's own directory, and the Dockerfile's `COPY` paths are relative to the build context, not the Dockerfile's location; moving these files changed those resolutions, not just their address:
  - `Dockerfile` — multi-stage build (SDK → aspnet runtime) for `MyApplication.Api`, listens on port 8080 in the container. Restore is scoped to `dotnet restore .../MyApplication.Api.csproj` (not the whole `.sln`), so it only needs `.csproj` files for projects `MyApplication.Api` actually references — currently Api, Application, Infrastructure, Domain. Add a new `COPY ... .csproj` line here whenever a new project is added to *that* dependency graph; `MyApplication.Tests` (and any other project the shipped API doesn't reference) deliberately doesn't need one. Every compose file that builds this image sets `context: ..` (repo root — `COPY` paths inside the Dockerfile are written as `src/MyApplication/...`) and `dockerfile: ci/Dockerfile`, since context and Dockerfile location are two independent settings.
  - `Dockerfile.web-ui` — multi-stage build (`node:22-alpine` → `nginx:1.27-alpine`) for `MyApplication.Web.UI`: builds the Vite app (`npm ci --global=false && npm run build`), then copies `dist/` into an nginx image alongside `nginx.conf.template`. Same `context: ..` / `dockerfile: ci/Dockerfile.web-ui` convention as the API's `Dockerfile`. **Root `.dockerignore` excludes `**/node_modules/` and `**/dist/`** — without that, `COPY src/MyApplication.Web.UI/ ./` after `npm ci` would overwrite the container's freshly-installed Linux `node_modules` with the host's own (Windows) one, breaking native binary shims like `tsc` (`node.exe: not found` at build time) — hit and fixed once, don't drop that ignore rule. Also declares `ARG VITE_GOOGLE_CLIENT_ID` + `ENV VITE_GOOGLE_CLIENT_ID=$VITE_GOOGLE_CLIENT_ID` before `npm run build` — Vite bakes `VITE_*` vars into the static bundle at build time, not at container runtime, so this has to be a build arg (set via `docker-compose.app.yml`'s `build.args`), not an `environment:` entry like the API's config. The final stage copies `nginx.conf.template` to `/etc/nginx/templates/default.conf.template` (not straight to `conf.d/`) — the base image's own entrypoint script runs `envsubst` on anything there at container start (see `nginx.conf.template`'s own comment for why: the API's address differs per deploy target — container name in Docker Compose, private DNS in Railway) — and sets default `ENV PORT=80`/`ENV API_INTERNAL_ADDRESS=myapplication-api:8080` so Docker Compose usage needs no changes; a Railway deploy overrides both (`PORT` automatically, `API_INTERNAL_ADDRESS` manually, pointed at the API service's private networking address).
  - `nginx.conf.template` — serves the built UI's static files and reverse-proxies `/Notes` and `/Auth` to `http://${API_INTERNAL_ADDRESS}`, listening on `${PORT}` — same origin for the browser, so no CORS setup needed, and required for the refresh-token cookie to come back at all. Both are real environment variables substituted by the nginx image's `envsubst`-on-templates entrypoint (see `Dockerfile.web-ui` above) — nginx's own non-OS variables like `$host`/`$scheme`/`$uri` are untouched since envsubst only replaces variables that actually exist in the container's environment. If a new API route prefix is ever added that the UI calls, add a matching `location` block here.
  - `.dockerignore` — **deliberately stayed at the repo root, not moved into `ci/`**, unlike everything else here. Docker looks for it at the build *context* root (repo root, since `context: ..`), not next to the Dockerfile — moving it into `ci/` would silently stop it from being applied (no error, just a bigger/dirtier build context).
  - The app and its supporting services deploy as three **independent** Compose stacks, joined only by a shared external Docker network `elastic` (declared with `external: true` in the app/db stacks) — never merge them back into one file. `docker-compose.elk.yml` is the one that creates the network, so it must be started at least once before the other two:
    - `docker-compose.elk.yml` — single-node Elasticsearch + Kibana + APM Server (security disabled, dev-only). Owns/creates the `elastic` network. APM Server receives OTLP traces on `:8200` (gRPC and HTTP multiplexed on the same port) and writes them to Elasticsearch `traces-apm-*`, visible in Kibana under Observability → APM.
    - `docker-compose.db.yml` — single PostgreSQL instance (`postgres:17`), db/user/password all `myapplication`, port 5432. Just infra — no app-specific init scripts; the app applies EF Core migrations itself.
    - `docker-compose.app.yml` — `myapplication-api` plus `myapplication-web-ui` (nginx serving `MyApplication.Web.UI`, port 80, built from `ci/Dockerfile.web-ui`; depends on `myapplication-api` and shares the `elastic` network so nginx can resolve it by service name — see `nginx.conf.template` above). The API requires the `elastic` network (from the ELK stack) and, unlike the logging/tracing endpoints which degrade gracefully, requires `postgres` (from the db stack) to already be reachable — the app calls `Database.MigrateAsync()` on startup and will fail to start otherwise. `Google__ClientId`/`Jwt__SigningKey` (API) and the `myapplication-web-ui` build's `VITE_GOOGLE_CLIENT_ID` arg are real secrets/environment-specific values, so — unlike every other env var in this file, which is inlined literally — they're `${GOOGLE_CLIENT_ID}`/`${JWT_SIGNING_KEY}` shell-interpolated from a repo-root `.env` (gitignored; `.env.example` documents the two keys, Docker Compose loads `.env` from the directory it's invoked from automatically).
  - `docker-compose.load-tests.yml` — the standard k6 results stack: InfluxDB (metrics store, k6 writes to it via `--out influxdb=http://influxdb:8086/k6`) + Grafana (`localhost:3000`, anonymous Admin access — local-only tooling, never exposed). Fully self-contained/independent of the app's own `elk`/`db`/`app` stacks — k6 just needs network access to both this stack (to write results) and the running app (to generate load), so it's run with `--network myapplication-load-tests-infra_default` (the network this compose file creates) plus `BASE_URL` pointing at the host-published app port (the isolated load-test instance by default — see `docker-compose.load-tests-db.yml` below). Has an explicit top-level `name: myapplication-load-tests-infra` — without it, Docker Compose would derive the project (and thus default network) name from this file's own directory (`ci`) instead of the repo root, silently renaming the network to `ci_default` and breaking every hardcoded `--network myapplication-load-tests-infra_default` reference (`load-tests/scripts/Invoke-K6Scenario.ps1`'s default, the docs); the `-infra` suffix (rather than plain `myapplication-load-tests`) avoids colliding with `docker-compose.load-tests-db.yml`'s own project name below. Grafana auto-provisions on first start from `../load-tests/grafana/provisioning/` (InfluxDB datasource named `InfluxDB-k6`) and `../load-tests/grafana/dashboards/k6-load-testing-results.json` (the classic community "k6 Load Testing Results" dashboard, grafana.com id 2587 — downloaded once and hand-edited to replace its `${DS_K6}` template-variable datasource references with the literal `InfluxDB-k6` name, since file-based dashboard provisioning doesn't resolve those import-wizard template variables the way Grafana's UI import does). If that dashboard JSON is ever re-fetched/regenerated, redo that substitution or the panels will show "datasource not found".
  - `docker-compose.load-tests-db.yml` — a disposable, fully isolated Postgres + API instance (`postgres-loadtest` on host port 5433, `myapplication-api-loadtest` on host port 8081) used only while a k6 scenario is running, so `SEED_COUNT` (thousands of notes) never pollutes the real dev database (`docker-compose.db.yml`). No `elastic` network, no logging/tracing env vars — deliberately self-contained, unlike `docker-compose.app.yml`. Sets `ASPNETCORE_ENVIRONMENT=LoadTest` (not `Production`) — `Program.cs` checks that exact environment name to swap `IGoogleIdTokenValidator` for `LoadTestGoogleIdTokenValidator` (`MyApplication.Infrastructure/Auth/`), since real Google login isn't reachable/needed just to measure RPS; k6 scenarios then log in for real through `POST /Auth/google` with a fixed fake `idToken` (`load-tests/lib/auth.js`). Also sets `ConnectionStrings__Users` (missing here would make `AuthDbContext.MigrateAsync()` fall back to `appsettings.json`'s `localhost` default, which resolves to the container itself, not `postgres-loadtest` — the whole app fails to start) and `Jwt__AccessTokenLifetimeMinutes=60` (k6 logs in once per run and never refreshes, so the token must outlive the whole ramp). `load-tests/scripts/Invoke-K6Scenario.ps1` manages its whole lifecycle automatically (see the `load-tests/` → `scripts/` entry above) via `docker compose -p myapplication-load-tests -f ci/docker-compose.load-tests-db.yml up -d --build` / `... down -v` — the explicit `-p myapplication-load-tests` keeps it in its own Docker network/namespace rather than sharing `myapplication-load-tests-infra_default` with the other stacks (so it doesn't need the `name:` trick `docker-compose.load-tests.yml` needs above). `down -v` matters: without `-v` the named volume (`postgres-loadtest-data`) would survive and the next run wouldn't start from an empty database. Manual up/down commands for debugging are in the file's own header comment.
- **Railway deployment** (production, internet-facing) — no config-as-code file in this repo; wiring lives entirely in the Railway project (`myapplication`, workspace `rualert's Projects`, environment `production`), reusing `ci/Dockerfile`/`ci/Dockerfile.web-ui` unchanged as the build source. Three services: `Postgres` (managed `postgres-ssl` template, private-networking only), `api` (`build.builder=DOCKERFILE`, `build.dockerfilePath=ci/Dockerfile`, root directory left at repo root — same context assumption as the local Dockerfile — no public domain), `web-ui` (`build.dockerfilePath=ci/Dockerfile.web-ui`, the project's only public domain, `https://web-ui-production-5b19.up.railway.app`). Same same-origin/no-CORS design as `docker-compose.app.yml`: `web-ui`'s nginx is the sole entry point and proxies `/Notes`/`/Auth` to `api` over Railway's private network (`API_INTERNAL_ADDRESS=${{api.RAILWAY_PRIVATE_DOMAIN}}:8080`, see `ci/nginx.conf.template`'s lazy-resolve comment above — a static `proxy_pass` to a Railway private domain crashes nginx at startup if that domain isn't resolvable yet, e.g. right after the `api` service's first deploy). `api`'s `ConnectionStrings__Notes`/`ConnectionStrings__Users` both point at the `Postgres` service via `${{Postgres.PGHOST}}` etc. reference variables, with `SSL Mode=Require;Trust Server Certificate=true` appended (the `postgres-ssl` template enforces SSL with a self-signed cert). `web-ui`'s `VITE_GOOGLE_CLIENT_ID` references `${{api.Google__ClientId}}` rather than duplicating the value. `Elasticsearch__Uri`/`OpenTelemetry__OtlpEndpoint` are deliberately left unset — no ELK stack on Railway, and both are designed to degrade gracefully (see the `MyApplication.Api/Program.cs` entry above) — logs are read via `railway logs`, tracing is simply off. **Deploys are automatic on merge to `master`**: both `api` and `web-ui` are connected to the GitHub repo (`rualert/my-application`, branch `master`), each with its own watch paths (`api`: `/src/MyApplication/**` + `/ci/Dockerfile`; `web-ui`: `/src/MyApplication.Web.UI/**` + `/ci/Dockerfile.web-ui` + `/ci/nginx.conf.template`), so a docs-only merge deploys nothing — **if a change touches something a Dockerfile `COPY`s from outside those paths, add it to the service's watch paths, or the merge silently won't deploy**. Railway's own "Wait for CI" is deliberately **off** (explicit user decision): the gate is GitHub branch protection on `master` (PR required, checks `backend` + `web-ui` from `tests.yml` required, branch must be up to date). `enforce_admins` is off, so the repo admin can still push straight to `master`, skipping both the tests and the deploy gate. Manual redeploy still works with `railway up --service api|web-ui --detach -m "<message>"` from the repo root — the next auto-deploy from `master` overwrites it (CLI: `npm install -g @railway/cli`, `railway login`, `railway link --project myapplication`) — see `README.md`'s "Развёртывание в Railway" section for the exact commands and the full variable table.
- `src/MyApplication/MyApplication.sln` — the solution file.
- `src/MyApplication/MyApplication.Domain/` — Domain layer class library. Zero dependency on any other project or framework/web package (not even EF Core — no ORM annotations here per the Dependency Rule). Organized in feature folders (e.g. `Notes/`): entities enforce their own invariants through private setters + factory/mutator methods that validate and throw a domain-specific exception (e.g. `Note.Create`/`Note.Update` throwing `NoteValidationException`), never plain public setters. `Note.Title` is nullable by design: `Note.Create`/`Note.Update` normalize a `null`/empty/whitespace-only title to `null` ("note without a title", stored as SQL `NULL`) rather than rejecting it — only an over-long title (`MaxTitleLength`) throws. `Note.Version` is owned by the entity the same way: `Create` sets it to `InitialVersion` (1) and `Update` increments it, and nothing outside can assign it — the "is this edit based on the current version?" *decision* lives in `NoteService`, not here, since `Note` has no notion of who is calling. Normalizing in the entity (not the API/UI) keeps that invariant true for every client; the API's `CreateNoteRequest`/`UpdateNoteRequest.Title` are `string?` (a non-nullable `string` there would make MVC's implicit `[Required]` reject a body that omits `title` with a 400 before it ever reaches the Domain).
  - `DomainException.cs` (namespace `MyApplication.Domain`, no feature subfolder) — abstract base class for **every** exception that should be treated as a client error (400/401/403, see `DomainExceptionHandler.cs`) by the API, across both this layer and `MyApplication.Application`. **Rule: a business-rule/invariant violation raised directly from `MyApplication.Domain` must derive from `DomainException`** (e.g. `NoteValidationException : DomainException`). See `MyApplication.Api/DomainExceptionHandler.cs` for how this gets mapped to a response. `DomainException` itself carries no HTTP-status concept (that would leak a Presentation concern into Domain) — the handler maps by exception *type* instead.
- `src/MyApplication/MyApplication.Api/` — ASP.NET Core Web API project (Presentation layer). Entry point: `Program.cs`, which wires up DI (registering `Application` layer services and their `Infrastructure` implementations — this is the only place allowed to reference `MyApplication.Infrastructure` directly), Serilog, OpenTelemetry tracing, EF Core (`AddDbContext`, one context per feature — `NotesDbContext` and `AuthDbContext`, both migrated on startup), JWT bearer auth (`AddAuthentication().AddJwtBearer()` + `AddAuthorization()`, validated against `Jwt:Issuer`/`Jwt:Audience`/`Jwt:SigningKey` — this is *our own* JWT, not Google's; Google is only consulted once, at login, via `IGoogleIdTokenValidator`), applies pending migrations on startup (`Database.MigrateAsync()` in a startup scope, before `app.Run()`), and registers global exception handling (`AddExceptionHandler<DomainExceptionHandler>()` + `AddProblemDetails()` + `app.UseExceptionHandler()`). Uses attribute-routed controllers (`AddControllers()` / `MapControllers()`), not minimal-API endpoints — all external call handlers live in `Controllers/`, calling into `MyApplication.Application` services/interfaces rather than containing business logic themselves; request/response DTOs live in `Models/` (distinct from the `Application` layer's own DTOs — map between them in the controller, e.g. `NotesController`, `AuthController`). `NotesController` is `[Authorize]`-protected and pulls the caller's id out of the JWT (`ClaimTypes.NameIdentifier`) rather than taking it as a request parameter.
  - `DomainExceptionHandler.cs` (namespace `MyApplication.Api`, root — not in `Controllers/`) — the single global exception handler: any `DomainException` (from Domain or Application) is mapped by a `switch` on its concrete type — `InvalidGoogleTokenException`/`InvalidRefreshTokenException` → 401, `NoteAccessDeniedException` → 403, `NoteConflictException` → 409, everything else (e.g. `NoteValidationException`, `NoteNotFoundException`) → 400 Bad Request — with the exception's message as the plain-text body. **Rule: controllers must not `catch` `DomainException`/`ApplicationException`/domain-specific exceptions themselves** — that mapping is centralized here on purpose, per explicit user instruction, so a controller action just calls the service and lets exceptions propagate. Adding a new exception type that needs a non-400 status means adding a case to this `switch`, not touching the exception type itself (no HTTP concept lives in Domain/Application). Anything that is *not* a `DomainException` is left unhandled by this handler and falls through to the generic `ProblemDetails` 500 response — verified live by stopping Postgres mid-request (a raw Npgsql connection failure, not a `DomainException`) and getting a 500. One consequence worth knowing: "not found" and "validation failed" are still not distinguishable by status code (both 400, unchanged) — only auth-related failures (401/403) and the version conflict (409) got their own codes.
  - Logging is configured in `Program.cs` via `Serilog` (`Serilog.AspNetCore`) + `Elastic.Serilog.Sinks`: writes to console and ships ECS-formatted logs directly to the Elasticsearch data stream `logs-myapplication-api-{environment}`. Elasticsearch endpoint comes from `Elasticsearch:Uri` (`appsettings.json`) / `Elasticsearch__Uri` env var.
  - Distributed tracing is configured in `Program.cs` via `OpenTelemetry.Extensions.Hosting` (`AddOpenTelemetry().WithTracing(...)`), with `AddAspNetCoreInstrumentation()` + `AddHttpClientInstrumentation()` + `AddNpgsql()` (from `Npgsql.OpenTelemetry`, covers every Postgres command executed through `NotesDbContext`) and an OTLP exporter. This propagates W3C `traceparent` across every incoming request and every outgoing `HttpClient`/Postgres call, and the trace/span IDs are auto-stamped onto Serilog/ECS log lines, so logs and traces correlate by `trace.id`. OTLP endpoint comes from `OpenTelemetry:OtlpEndpoint` (`appsettings.json`) / `OpenTelemetry__OtlpEndpoint` env var; if unset/unreachable, tracing is silently skipped.
  - **Rule: whenever a new outbound integration is added (a database client, a message queue producer/consumer, a call to another HTTP/gRPC service, etc.), add the matching OpenTelemetry instrumentation package for it in the same change** (e.g. Npgsql's native `Npgsql.OpenTelemetry`/`AddNpgsql()` or `OpenTelemetry.Instrumentation.EntityFrameworkCore` for Postgres/EF Core; the relevant instrumentation package for whatever message queue client is chosen), and register it in the `WithTracing(...)` call in `Program.cs`. Don't ship a new integration without tracing wired up — otherwise that hop becomes invisible in the trace.
  - Postgres connection strings: `ConnectionStrings:Notes` / `ConnectionStrings:Users` (`appsettings.json`) / `ConnectionStrings__Notes` / `ConnectionStrings__Users` env vars — one per feature's `DbContext`, both currently pointing at the same physical database by default. Unlike logging/tracing, these are a hard requirement — the app fails to start if Postgres isn't reachable (migrations). `Google:ClientId` and `Jwt:{Issuer,Audience,SigningKey,AccessTokenLifetimeMinutes}` are the other Auth-specific config — `SigningKey` is a real secret (not committed; empty placeholder in `appsettings.json`, real value via env var, same convention as everything else here).
  - API docs: `AddOpenApi()`/`MapOpenApi()` (built-in `Microsoft.AspNetCore.OpenApi`, no Swashbuckle) serves the raw spec at `/openapi/v1.json`; `Scalar.AspNetCore`'s `MapScalarApiReference()` serves an interactive UI at `/scalar` on top of it. Both are mapped only inside `if (app.Environment.IsDevelopment())` — not available when `ASPNETCORE_ENVIRONMENT=Production` (i.e. not in the Docker Compose/plain-`docker` deployments as currently configured).
- `src/MyApplication/MyApplication.Application/` — Application layer class library. Zero dependency on `MyApplication.Api`, `MyApplication.Infrastructure`, or any framework/web package (does depend on `MyApplication.Domain`). Organized in feature folders (e.g. `Notes/`, `Auth/`), each holding its DTOs (e.g. `NoteSummary.cs`/`NoteDetails.cs` — distinct from `MyApplication.Api/Models/` and from the `MyApplication.Domain` entity), a port interface for anything Infrastructure needs to implement (e.g. `INoteRepository.cs`, `Auth/IGoogleIdTokenValidator.cs`, `Auth/IJwtTokenGenerator.cs`), an application-level exception for use-case-level failures like "not found" (e.g. `NoteNotFoundException.cs` — as opposed to entity-invariant failures, which are `MyApplication.Domain` exceptions), and the use-case implementation (e.g. `NoteService.cs` implementing `INoteService`, `Auth/AuthService.cs` implementing `Auth/IAuthService.cs`). Register new services in `MyApplication.Api/Program.cs`'s DI container. `SearchAsync` is the odd one out in this layer: the relevance ranking it promises (exact-in-title → exact-in-text → similar-title → similar-text, see its XML docs on `INoteRepository`) is expressed as SQL inside `NoteRepository`, not as C# here — sorting by relevance and taking the top 10 in memory would mean reading every note of the user. What *is* here is `SearchSnippetBuilder` (pure, no EF/SQL): it locates the match in the title/text the same way the storage does (exact substring first, then the most similar word window by trigrams — a note found by a typo has no exact occurrence to highlight), cuts ~150 characters around it on word boundaries and returns `HighlightedSegment` lists. `NoteService`'s every method takes a leading `Guid callerUserId` (explicit parameter, not an ambient/injected current-user accessor — deliberately kept simple/explicit and easy to test without a fake) since notes are per-user-private; ownership mismatch (note exists, but not the caller's) throws `NoteAccessDeniedException`, distinct from `NoteNotFoundException`. `UpdateAsync` also takes a trailing `int expectedVersion` and throws `NoteConflictException` when it doesn't match `Note.Version` — this check has to live here (not only as the EF concurrency token) because `UseCasesTests`' EF InMemory provider ignores concurrency tokens entirely, and because it's the *client's* staleness being detected, not a race between two in-flight `SaveChanges` calls.
  - `Auth/IUserRegistrationHandler.cs` + `Notes/WelcomeNote.cs` + `Notes/WelcomeNoteRegistrationHandler.cs` — the welcome note for a new user. The port lives in `Auth` (`AuthService` calls `OnUserRegisteredAsync(userId)` only in the "user didn't exist yet" branch, right after the user is saved), the implementation in `Notes` (calls `INoteService.CreateAsync` with `WelcomeNote.Title`/`WelcomeNote.Text`), registered in `Program.cs` — so `Auth` knows nothing about notes and the dependency points from `Notes` to `Auth`'s port, not the reverse. `WelcomeNote.Text` is Markdown (the UI renders it in view mode; links must be explicit `[text](url)`, `react-markdown` without GFM doesn't autolink bare URLs) and is normalized to `\n` line endings, since the raw string literal would otherwise carry whatever the file on disk has (CRLF in a Windows checkout). Its last section is the hotkey list (`## Горячие клавиши`) — update it whenever a shortcut is added or changed (`WelcomeNoteTests` pins it as the last section); Markdown without GFM, so a list, not a table. That list lives in **three** places that must stay in sync: here, `docs/docs/notes/web-ui.md` («Горячие клавиши», the spec), and the in-app help window (`MyApplication.Web.UI`'s `notes/components/HotkeysHelp.tsx`). One deliberate omission from the two user-facing lists (the welcome note and the help window): the title↔text keys (Enter/↑/↓), since the title reads as the first line of the text and needs no prompting — explicit user decision, don't "complete" the list with them. Only new users get it — existing users were deliberately left alone, and deleting it doesn't bring it back. **Registration and the note are deliberately not atomic** (explicit user decision, argued at length in the comment in `AuthService.LoginWithGoogleAsync` and in `docs/docs/auth/business-rules.md`): two separate `DbContext`s, no shared transaction, so a failure creating the note leaves a user without one for good. Don't "fix" this with a shared transaction/`UseTransaction` across the two contexts — that would weld two bounded contexts into one unit of work; the way to a guarantee, if ever needed, is a transactional outbox. Also considered and rejected for a stricter invariant: saving the note *before* the user (an orphan note on failure instead of a note-less user).
  - `ApplicationException.cs` (namespace `MyApplication.Application`, no feature subfolder) — abstract base class for **every** exception thrown from this layer, itself deriving from `MyApplication.Domain.DomainException` (so it's covered by the same global exception handler, mapped to 400/401/403 by type — see the `MyApplication.Api` entry below). **Rule: every new Application-layer exception must derive from `MyApplication.Application.ApplicationException`, not directly from `Exception`** (e.g. `NoteNotFoundException : ApplicationException`). This is a project-local type, unrelated to `System.ApplicationException` from the BCL — the two share a name and resolve differently depending on context (our type wins via enclosing-namespace lookup for code inside `MyApplication.Application.*`, without needing a `using`), which is intentional per an explicit user request but worth remembering when reading/writing code here.
- `src/MyApplication/MyApplication.Infrastructure/` — Infrastructure layer class library. Depends on `MyApplication.Application` (implements its port interfaces) and `MyApplication.Domain`, plus whatever external/framework packages a given integration needs; never depends on `MyApplication.Api`. Organized in feature folders mirroring the `Application` port they implement, e.g. `Notes/`: `NotesDbContext` (EF Core `DbContext`, entity mapping in `OnModelCreating` — no attributes on the `Domain` entity itself) + `NoteRepository` (implements `INoteRepository`) + `Notes/Migrations/` (EF Core migrations, see the `dotnet ef migrations add` command in `README.md`). Remember the tracing rule above whenever a new integration is added here. `Auth/` mirrors this for the Auth feature: `AuthDbContext` (own `DbSet<User>`/`DbSet<RefreshToken>`, own `Auth/Migrations/`, own connection string `ConnectionStrings:Users`) + `UserRepository`/`RefreshTokenRepository` + `GoogleIdTokenValidator` (wraps `Google.Apis.Auth`'s `GoogleJsonWebSignature.ValidateAsync`) + `JwtTokenGenerator` (signs *our own* JWTs via `System.IdentityModel.Tokens.Jwt`, unrelated to Google) + `LoadTestGoogleIdTokenValidator` (derives a `GoogleUserInfo` straight from the given `idToken`, no real Google call — registered by `Program.cs` instead of `GoogleIdTokenValidator` only when `ASPNETCORE_ENVIRONMENT=LoadTest`, i.e. only in `ci/docker-compose.load-tests-db.yml`'s isolated stand; see the `load-tests/` entry above). `NotesDbContext` maps `Note.Version` with `.IsConcurrencyToken()`, so EF puts it in the `UPDATE`'s `WHERE` and `NoteRepository.SaveChangesAsync` translates the resulting `DbUpdateConcurrencyException` into `NoteConflictException` — that's the second, narrower half of the optimistic-concurrency story (the race *between* `NoteService`'s version check and its `SaveChanges`); the first half is the explicit check in `NoteService` itself. `NoteRepository.SearchAsync` is the one place in this codebase with hand-written SQL (`FromSql`): it needs `pg_trgm`'s `word_similarity`/`<%`, which LINQ can't express, and the whole point is to let the database rank and `LIMIT` instead of pulling rows into memory. `NotesDbContext` declares `HasPostgresExtension("pg_trgm")` plus two GIN indexes (`HasMethod("gin").HasOperators("gin_trgm_ops")`) on `Title`/`Text` — they serve both `ILIKE '%...%'` and `<%`, a B-tree index helps neither. The weights in its `ORDER BY` (4 / 2 / 1.5 / 1) encode a deliberate decision: **accuracy beats field**, i.e. an exact hit in the text outranks a merely similar title — changing them changes documented behaviour (`docs/docs/notes/business-rules.md`) and breaks `IntegrationTests/Notes/SearchNotesTests`. Note the EF InMemory provider used by `UseCasesTests` ignores all of this (extension annotation, index method, and `FromSql` itself), which is exactly why search is tested in `IntegrationTests/` instead. `Note.UserId` references `AuthDbContext`'s `users` table **by id only, no FK** — the two contexts are separate bounded contexts/`DbContext`s pointed at the same physical database, and EF can't enforce a cross-context FK anyway; this is intentional, not an oversight.
  - **One Postgres schema per `DbContext`**: `AuthDbContext.SchemaName` = `auth` (`users`, `refresh_tokens`), `NotesDbContext.SchemaName` = `notes` (`notes`), each set via `HasDefaultSchema`; nothing lives in `public` except the `pg_trgm` extension (it's created without a schema, so it lands in `public`, which stays on the `search_path` — that's why `word_similarity`/`<%`/`gin_trgm_ops` still resolve from the `notes` schema). **Each context also has its own migrations-history table in its own schema** (`auth."__EFMigrationsHistory"`, `notes."__EFMigrationsHistory"`; before, both shared `public`'s). That's configured in exactly one place per context — its static `ConfigureNpgsql(options, connectionString)`, which `Program.cs` and `IntegrationTests/Harness/PostgresFixture` both call instead of a bare `UseNpgsql` — because a context created without it would look for its history in `public`, find nothing and re-run `InitialCreate`. Schemas are bounded-context boundaries in the DB, not isolation: one DB user still sees both, and there's still no cross-schema FK (`Note.UserId`, see below) and no shared transaction between the two contexts. Things that reference the schema by name and must be updated together with `SchemaName`: the raw SQL in `NoteRepository.SearchAsync` (`FROM notes.notes` — a schema name can't be a query parameter) and both Respawn setups in the tests. **Migrations were squashed when this was introduced** — one `InitialCreate` per context, created directly in its schema (explicit user decision: no backward compatibility, the old database was wiped by hand). Consequence worth remembering: an environment that still has the pre-schema layout can't be upgraded in place — the empty per-schema history makes EF re-run `InitialCreate` against the existing `public.notes`/`public.users`, and the app dies on startup; drop the database (Railway's `Postgres` service, or `docker compose -f ci/docker-compose.db.yml down -v` locally) before the first start on the new build. `dotnet ef migrations add` needs `--context` now (two contexts) — commands in `README.md`. Note the first start on an *empty* database logs two `ERR` `Failed executing DbCommand` lines for `SELECT ... FROM <schema>."__EFMigrationsHistory"` — EF probing a history table that doesn't exist yet; benign, gone on the second start.
  - `Npgsql.EntityFrameworkCore.PostgreSQL` here and `Microsoft.EntityFrameworkCore.Design` in `MyApplication.Api` **must stay on matching EF Core versions** (currently both effectively on EF Core 10.0.4) — a mismatch produces an MSB3277 assembly-version-conflict warning at build time (harmless at runtime, but a smell) and can make `dotnet ef` misbehave. When bumping one, bump the other to match.

Requirements live in `docs/docs/notes/android.md` and are the spec here too, same rule as for `MyApplication.Application`/`Web.UI`. Application id `io.github.rualert.mynotesapp`, minSdk 26, compileSdk 37 (current AndroidX/Compose refuse anything lower), targetSdk 36 (deliberately behind — it opts the app into new *runtime* behaviour and should be raised on purpose, not along with compileSdk); Retrofit + OkHttp + `kotlinx.serialization` for the API, Credential Manager for the Google login, DataStore for the refresh cookie. Build with `gradlew.bat assembleDebug` (APK in `app/build/outputs/apk/debug/`), see `src/MyApplication.Android/README.md`.
  - **Dependency injection is hand-rolled** (`AppContainer`, built in `MyNotesApplication.onCreate`), no Hilt/Koin — the graph is a dozen objects and exactly one instance of it, and Hilt would add annotation processing to the build for that. Same taste as the rest of the repo (no NetArchTest, no Swashbuckle, no `@react-oauth/google`).
  - Auth deliberately mirrors `MyApplication.Web.UI`'s `api/client.ts`: access token in memory only (`TokenStore`), refresh token in the httpOnly cookie the API sets, `AuthInterceptor` adding `Authorization: Bearer` and retrying **once** after a refresh on a 401, `/Auth/*` exempt from both. Two things differ from the browser: the cookie has to be stored by the app itself (`SessionCookieJar` + `CookieStorage` over DataStore — a browser would do this), and that cookie's `SameSite=Strict` is irrelevant here, being a browser rule about cross-site requests rather than a requirement on clients. `AuthRepository.refreshSession` takes the token whose 401 triggered it, so parallel 401s don't each rotate the refresh token. A third difference is deliberate and *not* shared with the web: **a failed refresh is split by cause** — only a 401 clears the stored cookie and shows the login screen; an `IOException`/5xx leaves it intact and yields `SessionState.Unavailable` (a "нет связи / Повторить" screen), because on a phone the network drops constantly and losing the login to a lift ride is not acceptable. For the same reason `restoreSession` skips the request entirely when no cookie was restored (fresh install → login screen with no network round-trip), and OkHttp gets a 15-second `callTimeout` — the default has no whole-call bound, and a stalled call otherwise leaves the user staring at a spinner (observed: 21 s against Railway from the emulator). **The end of a session wipes that session's data** — explicit logout and a 401 on `/Auth/refresh` alike: `AuthRepository.endSession` calls the `SessionEndListener` port (declared in `data/auth`, wired in `AppContainer.forgetSessionData`, same direction as the backend's `IUserRegistrationHandler` — auth knows nothing about notes), which cancels the `SyncWorker` unique work, deletes every row including unsent ones (`NotesSyncer.forgetAll`, under the same `exchange` mutex so a page fetched in the old session can't land after the wipe) and cancels conflict notifications. Before this, the next person to log in on the phone saw the previous user's notes, and the previous user's queued offline edits were pushed under the new user's token. The listener must not wait for that work (it's launched on the app scope): a session end is often discovered *inside* a push, whose request got the 401, and waiting for the push from within it deadlocks. Losing unsent edits when a session merely expires is a deliberate trade-off, not an oversight — telling "same user back" from "someone else" would need the user id on the device. `NotesViewModel` lives in `AuthViewModel.sessionViewModels` (provided to `NotesScreen` as `LocalViewModelStoreOwner` by `AppRoot`), not in the activity's store: it's cleared the moment the session leaves `LoggedIn`, yet survives rotation because `AuthViewModel` does — in the activity's store it outlived logout, draft and autosave timer included.
  - **The backend needs no changes for Google login**: Credential Manager is given the *web* client id as `serverClientId`, so the ID token's `aud` is the one `GoogleIdTokenValidator` already checks against `Google:ClientId`. What Google does need is an extra OAuth client of type **Android** in the same Google Cloud project (`mynotesapp-509010`), registered with the package name and the SHA-1 of every keystore that signs the APK (debug and release are separate entries) — without it the system dialog refuses to issue a token. The client id itself is build config kept out of git, like `VITE_GOOGLE_CLIENT_ID`: `myNotesApp.googleServerClientId` in `local.properties` (or `-P`, or a CI secret), with an empty placeholder in `gradle.properties`. `myNotesApp.apiBaseUrl` works the same way and defaults to the Railway deployment.
  - **AGP 9 brings Kotlin itself**: applying `org.jetbrains.kotlin.android` is now a hard build error ("no longer required for Kotlin support since AGP 9.0"), so the root/app build files apply only `com.android.application` plus the two Kotlin *compiler* plugins that aren't part of that (`plugin.compose`, `plugin.serialization`). `jvmTarget` needs no setting either — with built-in Kotlin it defaults to `compileOptions.targetCompatibility`.
  - Gotcha that cost a build cycle and looks nothing like its cause: **Kotlin block comments nest**, so a `/*` inside a KDoc (here: the literal path `/Auth/` followed by a star, written in a comment) opens a nested comment, the file's closing `*/` closes only that one, and the whole file after it silently stops existing. The visible error was `Unresolved reference 'AuthInterceptor'` in a *different* file; the real message (`Syntax error: Unclosed comment`) was one line among many in the task output. Don't write glob-looking paths in Kotlin comments.
  - UI is Compose + Material 3, one `NotesViewModel` owning the list, the open note and autosave; `NotesScreen` swaps between the list and the editor (both via system Back), `NoteEditorScreen`/`NotesListScreen` are the two panes. Autosave repeats the web's contract exactly (5 s after the *first* unsaved change, the timer is not reset by further typing, plus an immediate save on leaving the note and on `ON_STOP`), saves are single-flight through a `Mutex`, and a 409 sets `hasConflict`, which stops autosave until the user picks a side. `flushSave()` takes a **snapshot** of the draft (`PendingSave`) rather than saving "whatever is open now" — otherwise switching notes would either block on the previous note's PUT or send the new note's text under the old note's id.
  - **Offline-first storage** (`data/local/`, Room): the device holds the notes, the server is what they are eventually reconciled with — the one part of this client with no counterpart in the web UI. Two decisions shape everything else. First, the primary key is a **local** id minted on creation, with the server id kept in a separate nullable column: a note exists (and can be edited, opened, deleted) before the server knows about it, and the UI's reference to it never has to be re-pointed when it is finally created remotely. Second, the outbox is **per row** (`pendingOperation`: None/Create/Update/Delete) rather than a log of operations — for notes it collapses to the same thing and avoids replaying a queue. `NotesSyncer.push()` walks pending rows oldest-first and stops at the first `IOException` so a later edit can't overtake the create of the same note; `pull()` merges a server page without touching rows that have unsent changes, and treats a synced note missing from the page as deleted elsewhere **only inside the `createdAt` range that page covers** (`CoveredRange`: unbounded above for the first page, below for a short/last one, ends exclusive) — it used to be the whole first page, so every refresh (i.e. every app start) wiped everything past the first 50 notes off the device. That range relies on the server sorting by `CreatedAt` and on local `createdAt` being the server's, which is why `applyPushed` adopts `createdAt` from the response too (a note created on the device carried the phone's clock). `SyncWorker` (WorkManager, network constraint, `APPEND_OR_REPLACE`) runs it, so an edit made underground uploads itself later even if the app was closed meanwhile. A 409 during that deferred push marks the row and raises a **notification** (`ConflictNotifier`, `POST_NOTIFICATIONS`), because waiting for the user to reopen the app could mean waiting a day while the other device keeps editing; tapping it opens that note with the same two-button warning as an online conflict. The editor shows «Не отправлено» while a row is pending. Search deliberately stays online-only — it is Postgres' trigram ranking, and a second, different local search would find different things. **Rule learned the hard way: nothing in `data/` may read a row, modify it and write it back outside a transaction.** Three code paths did (`saveDraft`, `deleteNote`, both conflict resolutions) plus the syncer writing the push response by the entity it had sent, and every one of them was a way to lose an edit typed while a request was in flight — the response landed last and took the text *and* the `pendingOperation` with it, so the editor still showed the edit while the device no longer had it. All of these now live in `NotesDao` as `@Transaction` methods that re-read the row (`saveDraft`, `markForDelete`, `replaceWithServer`, `keepMineWithVersion`, `applyPushed`, `markConflicted`); `applyPushed` keeps the local text and the queue entry when the row changed since the push but still adopts the response's version, so the next attempt isn't a spurious 409. For the same reason `NotesSyncer` serializes `push()` and `pull()` through one `Mutex`: two pushes could send the same edit twice (the second got a 409 and left a successfully saved note stuck «не отправлено» forever), and a page fetched before a delete could resurrect the note under a new local id. And `NotesViewModel` takes `hasConflict` from the database in **both** directions — when it only ever set the flag, a late emission about an already-resolved conflict brought the warning back and silently stopped autosave for good.
  - Search (`GET /Notes/search`) replaces the list in place: the toolbar's search button swaps the top bar for a full-width field and the list for the results. Unlike the web it is **one-step** — a tap opens the note and closes search — because the two-step preview/commit dance exists to keep a keyboard-driven result list alive, which a finger doesn't need (see the comparison table in `docs/docs/notes/android.md`). The 300 ms debounce is the web's idea reused; highlighting arrives from the server as `{text, match}` segments (`HighlightedText` gives `match` ones a background), since a note found through a typo contains no literal occurrence to highlight. `NotesSearchState.isSearching` means **"a request is in flight"**, deliberately not "the user is typing" — otherwise «Идёт поиск…» would flash on every keystroke and the debounce would have no observable effect to test. Back peels one layer at a time: out of search first, then from the note to the list (two `BackHandler`s with mutually exclusive `enabled`).
  - `rememberNow()` (the 30-second tick behind "Сохранение: N минут назад") lives in the composable, not the ViewModel. An endless `while (true) { delay(...) }` inside a ViewModel **hangs every `runTest`**: at the end of a test the framework advances virtual time until the scheduler is idle, and an infinite timer never is. Cost a long debugging detour; don't move it back.
  - Icons: `androidx.compose.material:material-icons-core` is declared explicitly with its own version — material3 1.4 stopped depending on it, and the icon artifact is frozen at 1.7.8, so the Compose BOM does not manage it either.
  - **Tests** (`app/src/test/kotlin/...`, JUnit 4 + `kotlinx-coroutines-test` + MockWebServer; `gradlew testDebugUnitTest`, also run in `.github/workflows/android.yml`): same philosophy as the rest of the repo — only the network boundary is replaced (`NotesTestBackend`, an in-memory API that enforces the real version check and answers 409, the analogue of MSW's `FakeNotesBackend` in the web UI), while `NotesRepository`, Retrofit, JSON parsing and the ViewModel are real. Style rules carry over (`Harness/`-style `harness` package, `Sut`, `// Arrange`/`// Act`/`// Assert`). `NotesTestBackend` guards all of its state with one lock and handles a request entirely inside it, so for the test thread a request is atomic — «the request was recorded» always implies «it was applied». It can also hold responses (`holdSearches()`, `holdUpdates()` — the latter applies the request and delays only the answer, which is the window an edit used to be lost in) and wait for background pushes started by a save (`awaitSyncIdle()`, needed whenever a test checks what its *own* explicit `syncNow()` returned). `awaitUntil` takes an optional `diagnostics` lambda printed on timeout — a failure that only reproduces on a two-core CI runner is otherwise undebuggable, and that lambda is what found the lost-edit bug above. Two gotchas found by mutation-testing the suite, both of which silently made tests pass against deliberately broken code:
    - **`runTest` advances virtual time on its own** whenever the test body suspends (e.g. waiting for a real MockWebServer response). So a test that "waits for the save" cannot prove *when* the save was scheduled — a debounce would pass too. Timing assertions must therefore be made **without suspending**: `advanceTimeBy(...)` + `runCurrent()` + assert.
    - A corollary that bit twice (autosave, then the search debounce): **"no request was sent yet" is not observable here.** Waiting for a real response lets `runTest` advance virtual time, and a client-side cancel races the socket, so the fake server may or may not record a request the client abandoned. Both times the fix was to give the production code an honest synchronous signal (`editor.isSaving`, `search.isSearching`) and assert on that instead.
    - Assert on the **client's** state, not the fake server's. `editor.isSaving` flips synchronously when a request starts, whereas `backend.updates` only grows once the request reaches the server — checking the latter right after `runCurrent()` would see nothing either way. The same applies to deletes: wait for the list/editor to change, not for the note to vanish from the fake backend (that happened before the client saw the response, and made one test flaky).
    - `Dispatchers.setMain` gets an `UnconfinedTestDispatcher` sharing the scheduler of the `StandardTestDispatcher` that `runTest` uses: with a Standard dispatcher for Main, the ViewModel's coroutines never ran while the test body held the dispatcher, and every wait timed out.
    - `mockwebserver3`'s `RecordedRequest.body` is nullable (`ByteString?`).
    - Since M4 the tests run under **Robolectric** (`@RunWith` on the shared base class, inherited): the store is real SQLite, and an in-memory Room database is the honest substitute. `NotesTestBackend` now owns the database and a `SyncScheduler` that pushes immediately, so "online" behaves as it does in the app.
    - **Simulate "no network" in the OkHttp client, not in MockWebServer.** Shutting the socket from the dispatcher was read by Retrofit as a *successful empty response*, so "delete while offline" silently counted as done — the queue emptied and the note stayed on the server. An interceptor that throws `IOException` is both simpler and faithful. The mistake was in the harness, and it was hiding a would-be product bug rather than finding one.
    - Teardown order matters now: cancel the ViewModel's scope, then `cancelAndJoin` the harness's sync scope, then close the database. Cancellation is asynchronous, so without the join an in-flight push lands on a closed database — and the failure surfaces in whatever test runs *next*, as `UncaughtExceptionsBeforeTest`.
    - Two flakes worth remembering, both in test timing rather than in the code: a note added to the fake server *after* the app has already loaded its list never arrives unless the test asks for a refresh (hence `openServerNote` calls `refresh()` itself); and `isPending` is true from the moment a note is created, so it can't be used to wait for a later edit to reach the device — wait for the edit itself.
  - Local-build gotcha, already hit once: this machine's `PATH` resolves `java` to an ancient Oracle JRE 8 (`C:\ProgramData\Oracle\Java\javapath`) whose truststore can't validate `services.gradle.org`, so `gradlew` dies with `PKIX path building failed` before it has even downloaded Gradle. `JAVA_HOME` is set machine-wide to Microsoft OpenJDK 21 and `gradlew` prefers it — this only bites in a shell started before that variable existed.

## Working with this repo

From `src/MyApplication/`:
- `dotnet build` — build the solution
- `dotnet run --project MyApplication.Api` — run the API
- `dotnet test` — run all tests (`MyApplication.Tests`)

From `src/MyApplication.Web.UI/`:
- `npm run dev` — dev server with hot reload, `http://localhost:5173` (proxies `/Notes` to the locally-run API on `:5184`)
- `npm run build` — type-check + production build to `dist/`
- `npm test` — frontend tests (Vitest); `npm run test:watch` for watch mode

From `src/MyApplication.Android/`:
- `.\gradlew.bat assembleDebug` — build the APK (`app/build/outputs/apk/debug/`)
- `.\gradlew.bat installDebug` — build and install it on the connected device
- `.\gradlew.bat testDebugUnitTest` — unit tests (no device or emulator needed)

## Architecture role and rules

Role: You are an expert software architect specializing in Clean Architecture and Domain-Driven Design (DDD).

Strict Rules for Code Generation:
1. Architectural Layers: Always separate the codebase into distinct layers:
   - Domain (Enterprise business rules: Entities, Value Objects, Use Case Interfaces). Must have zero dependencies on other layers or external libraries.
   - Application (Application business rules: Use Case implementations, CQRS handlers, DTOs, Port interfaces for infrastructure).
   - Infrastructure (Frameworks, Database/ORM implementations, External APIs, Adapters).
   - Presentation (UI, Controllers, Presenters, API Endpoints).

2. Dependency Rule: Source code dependencies must only point inwards. Outer layers (Infrastructure/Presentation) can depend on inner layers (Application/Domain), but inner layers must NEVER depend on outer layers. Use Dependency Inversion (Interfaces) to achieve this.

3. Code Standards:
   - Write clean, maintainable, and heavily decoupled code.
   - Follow SOLID principles strictly.
   - Use meaningful names for classes and variables according to the domain.
   - Avoid mixing business logic with framework-specific code (e.g., no ORM annotations or HTTP status codes in the Domain layer).

Output Format:
- When asked to create a feature, explicitly structure your response by layers (Domain, Application, Infrastructure, Presentation).
- Provide the file paths and the exact code for each file.
- Explain briefly how the data flows between layers for the generated feature.
