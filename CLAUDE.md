# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

The solution `src/MyApplication/MyApplication.sln` has five projects: `MyApplication.Domain`, `MyApplication.Application`, `MyApplication.Infrastructure`, `MyApplication.Api` (Presentation) — a full Clean Architecture layering — plus `MyApplication.Tests` (xUnit, not shipped). Two use cases exist: `Notes`, a real CRUD feature spanning all four layers, backed by PostgreSQL via EF Core, and `Auth` — Google-login-based JWT authentication (own access + refresh tokens, Google itself only validates the initial ID token via `IGoogleIdTokenValidator`), which also makes `Notes` per-user-private (`Note.UserId`, no FK across the two features' DbContexts — separate bounded contexts, see `MyApplication.Infrastructure/Auth/` vs `MyApplication.Infrastructure/Notes/`). `DomainExceptionHandler` maps exceptions to 400/401/403/409 by type (see its own entry below), not a flat 400 like before. `Notes` also carries optimistic concurrency: `Note.Version` (int, `Note.InitialVersion` = 1, +1 per `Update`) is echoed back by the client on every `PUT`, and a mismatch is a 409 (`NoteConflictException`) instead of a silent overwrite — that's what keeps the same note open in two tabs from losing edits; see `docs/docs/notes/business-rules.md`. `Notes` also has **search** (`GET /Notes/search`, the search box in the UI header): matching and relevance ranking are done by Postgres itself via the `pg_trgm` extension (trigram similarity — that's what finds a note despite a typo in the query), while the snippet around the match and the highlighted ranges are built in the Application layer (`SearchSnippetBuilder`); see `docs/docs/notes/business-rules.md` («Поиск»). (An earlier `WeatherForecast` placeholder, inherited from the ASP.NET Core template, was deleted once it had no test coverage and no real business logic — don't recreate that pattern for new features.) A second Presentation surface, `src/MyApplication.Web.UI/` (React SPA), lives alongside the solution — a separate Node/npm project, not a `.sln` project — see its own entry in Structure below.

## Structure

- `README.md` — run instructions (local + Docker + Docker Compose/ELK + tracing + docs site).
- `docs/` — a separate [Docusaurus](https://docusaurus.io/) site documenting the application's **business logic** (use cases/business rules/API contracts), independent of this repo's technical README/CLAUDE.md. Content lives under `docs/docs/`, one folder per use case (currently just `notes/`, the CRUD notes feature), with `_category_.json` files controlling the sidebar tree — `sidebars.js` auto-generates the sidebar from that folder structure, so **adding a new use case is just adding a new folder** there. Has its own `package.json`/`node_modules`/`.npmrc` (Node/npm project, unrelated to the .NET solution) — `npm install --global=false && npm start` from `docs/`. `docs/.npmrc` forces local (non-global) installs — needed in some environments where a user-level npm config defaults `npm install` to global/misresolved locations; keep it even if your own environment doesn't need it. When real business logic is added to `MyApplication.Application`, add/update the corresponding page(s) under `docs/docs/` in the same change. **This also runs in reverse: treat `docs/docs/` as the spec.** If a change to `docs/docs/` describes new or different application behavior than what `MyApplication.Application` currently implements (not just wording/formatting edits), don't just accept the doc edit — point out the mismatch and propose the corresponding code change, and only implement it once the user confirms. Published automatically to GitHub Pages at `https://rualert.github.io/my-application/` by `.github/workflows/deploy-docs.yml` on every push to `master` touching `docs/**` — keep `docusaurus.config.js`'s `url`/`baseUrl` (`https://rualert.github.io` / `/my-application/`) in sync if the repo or org is ever renamed.
- `load-tests/` — [k6](https://k6.io/) load-test scenarios, plain JS, no `package.json`/build step, run via the `grafana/k6` Docker image or a local `k6` binary (not part of `MyApplication.Tests`, not restored/built by `dotnet`). One file per scenario under `scenarios/` (currently `notes-list.js` for `GET /Notes`, `notes-get-by-id.js` for `GET /Notes/{id}`, `notes-create.js` for `POST /Notes` — that one's own request load *is* the write being measured, `SEED_COUNT` there only sets the starting table size, not the thing under test), shared config in `config.js`, shared seeding helper in `lib/seed.js`, shared login helper in `lib/auth.js`. `/Notes` is JWT-protected and per-user-private (see `Auth`, below) — every scenario's `setup()` logs in once via `lib/auth.js`'s `loginLoadTestUser()` (a real `POST /Auth/google`) and attaches the resulting access token as `Authorization: Bearer` to every request (seeding and the load itself), so the whole run acts as one fixed load-test user. Real Google isn't reachable/needed just to measure RPS, so this only works against the isolated stand (`ci/docker-compose.load-tests-db.yml`, `ASPNETCORE_ENVIRONMENT=LoadTest`, see below) — that environment name makes `Program.cs` swap in `LoadTestGoogleIdTokenValidator` instead of the real Google validator (same trick as `FakeGoogleIdTokenValidator` in `SmokeTests`). One login per run, no refresh — `Jwt:AccessTokenLifetimeMinutes` is raised for that isolated stand accordingly (see below). Each scenario uses the `ramping-arrival-rate` executor to step the target RPS up (stages configurable via `STAGE_TARGETS`/`STAGE_DURATION` env vars) against `thresholds` (`http_req_failed`, `http_req_duration` p99) — the goal is finding the highest RPS stage that still meets both, not a pass/fail CI gate. Points `BASE_URL` at a real deployed instance, not `WebApplicationFactory`, since in-process hosting doesn't reflect real network/connection-pool behavior under load — by default that's the isolated instance from `ci/docker-compose.load-tests-db.yml` (see below and the `scripts/` entry), not the regular dev app.
  - `lib/seed.js` — seeds `SEED_COUNT` notes via `http.batch()` in batches of `BATCH_SIZE` (50), not one request at a time. **A large `SEED_COUNT` (thousands) with sequential seeding blows past k6's default `setupTimeout` (60s)**, aborting the whole run with `setup() execution timed out` before any load is generated — looks from the outside like the `SEED_COUNT` parameter was silently ignored. Batching plus each scenario's `options.setupTimeout: '5m'` (defense-in-depth on top of batching) fixes that. If `SEED_COUNT` ever needs to go well beyond ~10k, re-check the batch math rather than assuming this is still headroom.
  - `lib/stageThresholds.js` — tags every request with its current stage's target RPS (`stage_rps`, computed from `k6/execution`'s `currentTestRunDuration` — k6 exposes no public API to ask the `ramping-arrival-rate` executor which stage it's on) and duplicates each scenario's `thresholds` as per-stage submetrics (`http_req_duration{stage_rps:400}`, etc), not just the whole-run aggregate.
  - `lib/maxRpsSummary.js` — each scenario's `handleSummary()` calls into this to scan those per-stage submetric thresholds and print `Maximum RPS satisfying thresholds: <n>` straight to the console (the highest stage where every threshold still passed) — no need to eyeball Grafana just to find that number. Defining `handleSummary()` stops k6's automatic summary print, so this reconstructs it via jslib's `textSummary` (fetched from `jslib.k6.io` at run time — needs outbound network from the k6 container/binary, same as any other remote k6 import). Also appends a markdown table row (date, max RPS, the scenario's `thresholds` rules, `SEED_COUNT`) to `results/<scenario>.md` — see below; `thresholds`/`SEED_COUNT` ride along because both can change between runs and the RPS number alone is meaningless without knowing which pair it was measured under. **Real k6 quirk, not a bug: `open()` only works during the init stage** (script top-level, before any iteration/VU runs) — calling it from inside `handleSummary()` itself throws `"open function is only available in the init stage"`, since by then the run has finished. That's why each scenario reads its results-file history (`readResultsHistory()`) at its own top level and only passes the already-read string into `summarizeMaxRps()`/`handleSummary()` — don't move that call into `handleSummary()` to "simplify" it, it'll break. Also note `open()` and the `handleSummary()` output-object keys resolve relative paths *differently*: `open()` is relative to the calling script file (`scenarios/`, hence the `../results/...` prefix used there), while output-object keys are relative to the k6 process's cwd (`load-tests/`, hence the bare `results/...` used for the written path) — confirmed empirically, not documented clearly by k6 itself.
  - `results/notes-list.md`, `results/notes-get-by-id.md`, `results/notes-create.md` — a markdown table (`| Дата | Max RPS | Thresholds | Seed count |`), one row per run, appended (not overwritten) by the `handleSummary()` mechanism above. A history in git, independent of InfluxDB/Grafana retention.
  - See `load-tests/README.md` for exact run commands. Results are also viewed in Grafana for the full time-series picture — see the `ci/docker-compose.load-tests.yml` entry below.
  - `scripts/` — PowerShell wrappers around the `docker run ... grafana/k6 run ...` invocation, for convenience on this (Windows) dev machine. `Invoke-K6Scenario.ps1` does the actual `docker run` (takes `-ScenarioFile`, `-AppPort`, `-BaseUrl`, `-Network`, `-InfluxUrl`, `-SeedCount`, `-StageDuration`, `-StageTargets`, `-KeepDb`); `Invoke-NotesListScenario.ps1`/`Invoke-NotesGetByIdScenario.ps1`/`Invoke-NotesCreateScenario.ps1` are thin per-scenario wrappers that forward `$PSBoundParameters` to it plus their own `-ScenarioFile`. A new scenario needs its own such wrapper (copy an existing one, swap the `-ScenarioFile` literal and the `.SYNOPSIS`/`.EXAMPLE` text — nothing else differs). Any new param added to `Invoke-K6Scenario.ps1` must be copy-pasted into every wrapper's own `param()` block too, or passing it to a wrapper fails with "parameter not found" — `$PSBoundParameters` only forwards what the *wrapper itself* declares. **Gotcha already hit once: declare RPS-list parameters as `[string[]]` (joined with `,` before use), not `[string]`** — PowerShell parses an unquoted comma-separated value like `-StageTargets 10,20` into an array at the call site before binding, so a `[string]` parameter fails to bind for that (very natural, unquoted) calling style. Also handles k6's exit code **99** specially — that means "a threshold was breached," the expected/normal outcome of these scenarios (not a tooling failure), so it's reported via `Write-Warning` instead of a terminating `throw`; any other non-zero code still throws. **`Invoke-K6Scenario.ps1` also owns the lifecycle of `ci/docker-compose.load-tests-db.yml`** (see below): brings it up before the k6 run, polls `http://localhost:$AppPort/Notes` from the host until it responds with 2xx or 401 (no health endpoint/curl in the image for a Docker-level healthcheck, so this is done from PowerShell instead; 401 counts as ready too since `/Notes` is `[Authorize]`-protected and the probe has no token yet — a 401 still proves the app booted, migrations ran, and the auth pipeline is live), then tears it down (`down -v`) in a `finally` block regardless of how the k6 run went — unless `-KeepDb` is passed. Default `-BaseUrl` points at this isolated instance (`http://host.docker.internal:$AppPort`, `$AppPort` defaults to 8081), not the regular dev app on 8080.

- `ci/` — every Dockerfile / Docker Compose file lives here (moved out of the repo root once there were enough of them to be clutter — explicit user request). All commands below are run **from the repo root**, not from inside `ci/` (`docker compose -f ci/docker-compose.X.yml ...`, `docker build -f ci/Dockerfile ...`) — this matters because compose resolves a file's relative paths (bind mounts, build context) against the compose file's own directory, and the Dockerfile's `COPY` paths are relative to the build context, not the Dockerfile's location; moving these files changed those resolutions, not just their address:
  - `Dockerfile` — multi-stage build (SDK → aspnet runtime) for `MyApplication.Api`, listens on port 8080 in the container. Restore is scoped to `dotnet restore .../MyApplication.Api.csproj` (not the whole `.sln`), so it only needs `.csproj` files for projects `MyApplication.Api` actually references — currently Api, Application, Infrastructure, Domain. Add a new `COPY ... .csproj` line here whenever a new project is added to *that* dependency graph; `MyApplication.Tests` (and any other project the shipped API doesn't reference) deliberately doesn't need one. Every compose file that builds this image sets `context: ..` (repo root — `COPY` paths inside the Dockerfile are written as `src/MyApplication/...`) and `dockerfile: ci/Dockerfile`, since context and Dockerfile location are two independent settings.
  - `Dockerfile.web-ui` — multi-stage build (`node:22-alpine` → `nginx:1.27-alpine`) for `MyApplication.Web.UI`: builds the Vite app (`npm ci --global=false && npm run build`), then copies `dist/` into an nginx image alongside `nginx.conf.template`. Same `context: ..` / `dockerfile: ci/Dockerfile.web-ui` convention as the API's `Dockerfile`. **Root `.dockerignore` excludes `**/node_modules/` and `**/dist/`** — without that, `COPY src/MyApplication.Web.UI/ ./` after `npm ci` would overwrite the container's freshly-installed Linux `node_modules` with the host's own (Windows) one, breaking native binary shims like `tsc` (`node.exe: not found` at build time) — hit and fixed once, don't drop that ignore rule. Also declares `ARG VITE_GOOGLE_CLIENT_ID` + `ENV VITE_GOOGLE_CLIENT_ID=$VITE_GOOGLE_CLIENT_ID` before `npm run build` — Vite bakes `VITE_*` vars into the static bundle at build time, not at container runtime, so this has to be a build arg (set via `docker-compose.app.yml`'s `build.args`), not an `environment:` entry like the API's config. The final stage copies `nginx.conf.template` to `/etc/nginx/templates/default.conf.template` (not straight to `conf.d/`) — the base image's own entrypoint script runs `envsubst` on anything there at container start (see `nginx.conf.template`'s own comment for why: the API's address differs per deploy target — container name in Docker Compose, private DNS in Railway) — and sets default `ENV PORT=80`/`ENV API_INTERNAL_ADDRESS=myapplication-api:8080` so Docker Compose usage needs no changes; a Railway deploy overrides both (`PORT` automatically, `API_INTERNAL_ADDRESS` manually, pointed at the API service's private networking address).

Both are real environment variables substituted by the nginx image's `envsubst`-on-templates entrypoint (see `Dockerfile.web-ui` above) — nginx's own non-OS variables like `$host`/`$scheme`/`$uri` are untouched since envsubst only replaces variables that actually exist in the container's environment. If a new API route prefix is ever added that the UI calls, add a matching `location` block here.
  - `.dockerignore` — **deliberately stayed at the repo root, not moved into `ci/`**, unlike everything else here. Docker looks for it at the build *context* root (repo root, since `context: ..`), not next to the Dockerfile — moving it into `ci/` would silently stop it from being applied (no error, just a bigger/dirtier build context).
  - The app and its supporting services deploy as three **independent** Compose stacks, joined only by a shared external Docker network `elastic` (declared with `external: true` in the app/db stacks) — never merge them back into one file. `docker-compose.elk.yml` is the one that creates the network, so it must be started at least once before the other two:
    - `docker-compose.elk.yml` — single-node Elasticsearch + Kibana + APM Server (security disabled, dev-only). Owns/creates the `elastic` network. APM Server receives OTLP traces on `:8200` (gRPC and HTTP multiplexed on the same port) and writes them to Elasticsearch `traces-apm-*`, visible in Kibana under Observability → APM.

    - `docker-compose.app.yml` — `myapplication-api` plus `myapplication-web-ui` (nginx serving `MyApplication.Web.UI`, port 80, built from `ci/Dockerfile.web-ui`; depends on `myapplication-api` and shares the `elastic` network so nginx can resolve it by service name — see `nginx.conf.template` above). The API requires the `elastic` network (from the ELK stack) and, unlike the logging/tracing endpoints which degrade gracefully, requires `postgres` (from the db stack) to already be reachable — the app calls `Database.MigrateAsync()` on startup and will fail to start otherwise. `Google__ClientId`/`Jwt__SigningKey` (API) and the `myapplication-web-ui` build's `VITE_GOOGLE_CLIENT_ID` arg are real secrets/environment-specific values, so — unlike every other env var in this file, which is inlined literally — they're `${GOOGLE_CLIENT_ID}`/`${JWT_SIGNING_KEY}` shell-interpolated from a repo-root `.env` (gitignored; `.env.example` documents the two keys, Docker Compose loads `.env` from the directory it's invoked from automatically).

Fully self-contained/independent of the app's own `elk`/`db`/`app` stacks — k6 just needs network access to both this stack (to write results) and the running app (to generate load), so it's run with `--network myapplication-load-tests-infra_default` (the network this compose file creates) plus `BASE_URL` pointing at the host-published app port (the isolated load-test instance by default — see `docker-compose.load-tests-db.yml` below). Has an explicit top-level `name: myapplication-load-tests-infra` — without it, Docker Compose would derive the project (and thus default network) name from this file's own directory (`ci`) instead of the repo root, silently renaming the network to `ci_default` and breaking every hardcoded `--network myapplication-load-tests-infra_default` reference (`load-tests/scripts/Invoke-K6Scenario.ps1`'s default, the docs); the `-infra` suffix (rather than plain `myapplication-load-tests`) avoids colliding with `docker-compose.load-tests-db.yml`'s own project name below. Grafana auto-provisions on first start from `../load-tests/grafana/provisioning/` (InfluxDB datasource named `InfluxDB-k6`) and `../load-tests/grafana/dashboards/k6-load-testing-results.json` (the classic community "k6 Load Testing Results" dashboard, grafana.com id 2587 — downloaded once and hand-edited to replace its `${DS_K6}` template-variable datasource references with the literal `InfluxDB-k6` name, since file-based dashboard provisioning doesn't resolve those import-wizard template variables the way Grafana's UI import does). If that dashboard JSON is ever re-fetched/regenerated, redo that substitution or the panels will show "datasource not found".
  - `docker-compose.load-tests-db.yml` — a disposable, fully isolated Postgres + API instance (`postgres-loadtest` on host port 5433, `myapplication-api-loadtest` on host port 8081) used only while a k6 scenario is running, so `SEED_COUNT` (thousands of notes) never pollutes the real dev database (`docker-compose.db.yml`). No `elastic` network, no logging/tracing env vars — deliberately self-contained, unlike `docker-compose.app.yml`. Sets `ASPNETCORE_ENVIRONMENT=LoadTest` (not `Production`) — `Program.cs` checks that exact environment name to swap `IGoogleIdTokenValidator` for `LoadTestGoogleIdTokenValidator` (`MyApplication.Infrastructure/Auth/`), since real Google login isn't reachable/needed just to measure RPS; k6 scenarios then log in for real through `POST /Auth/google` with a fixed fake `idToken` (`load-tests/lib/auth.js`). Also sets `ConnectionStrings__Users` (missing here would make `AuthDbContext.MigrateAsync()` fall back to `appsettings.json`'s `localhost` default, which resolves to the container itself, not `postgres-loadtest` — the whole app fails to start) and `Jwt__AccessTokenLifetimeMinutes=60` (k6 logs in once per run and never refreshes, so the token must outlive the whole ramp). `load-tests/scripts/Invoke-K6Scenario.ps1` manages its whole lifecycle automatically (see the `load-tests/` → `scripts/` entry above) via `docker compose -p myapplication-load-tests -f ci/docker-compose.load-tests-db.yml up -d --build` / `... down -v` — the explicit `-p myapplication-load-tests` keeps it in its own Docker network/namespace rather than sharing `myapplication-load-tests-infra_default` with the other stacks (so it doesn't need the `name:` trick `docker-compose.load-tests.yml` needs above). `down -v` matters: without `-v` the named volume (`postgres-loadtest-data`) would survive and the next run wouldn't start from an empty database. Manual up/down commands for debugging are in the file's own header comment.

- `src/MyApplication/MyApplication.sln` — the solution file.
- `src/MyApplication/MyApplication.Domain/` — Domain layer class library. Zero dependency on any other project or framework/web package (not even EF Core — no ORM annotations here per the Dependency Rule). Organized in feature folders (e.g. `Notes/`): entities enforce their own invariants through private setters + factory/mutator methods that validate and throw a domain-specific exception (e.g. `Note.Create`/`Note.Update` throwing `NoteValidationException`), never plain public setters. `Note.Title` is nullable by design: `Note.Create`/`Note.Update` normalize a `null`/empty/whitespace-only title to `null` ("note without a title", stored as SQL `NULL`) rather than rejecting it — only an over-long title (`MaxTitleLength`) throws. `Note.Version` is owned by the entity the same way: `Create` sets it to `InitialVersion` (1) and `Update` increments it, and nothing outside can assign it — the "is this edit based on the current version?" *decision* lives in `NoteService`, not here, since `Note` has no notion of who is calling. Normalizing in the entity (not the API/UI) keeps that invariant true for every client; the API's `CreateNoteRequest`/`UpdateNoteRequest.Title` are `string?` (a non-nullable `string` there would make MVC's implicit `[Required]` reject a body that omits `title` with a 400 before it ever reaches the Domain).
  - `DomainException.cs` (namespace `MyApplication.Domain`, no feature subfolder) — abstract base class for **every** exception that should be treated as a client error (400/401/403, see `DomainExceptionHandler.cs`) by the API, across both this layer and `MyApplication.Application`. **Rule: a business-rule/invariant violation raised directly from `MyApplication.Domain` must derive from `DomainException`** (e.g. `NoteValidationException : DomainException`). See `MyApplication.Api/DomainExceptionHandler.cs` for how this gets mapped to a response. `DomainException` itself carries no HTTP-status concept (that would leak a Presentation concern into Domain) — the handler maps by exception *type* instead.
- `src/MyApplication/MyApplication.Api/` — ASP.NET Core Web API project (Presentation layer). Entry point: `Program.cs`, which wires up DI (registering `Application` layer services and their `Infrastructure` implementations — this is the only place allowed to reference `MyApplication.Infrastructure` directly), Serilog, OpenTelemetry tracing, EF Core (`AddDbContext`, one context per feature — `NotesDbContext` and `AuthDbContext`, both migrated on startup), JWT bearer auth (`AddAuthentication().AddJwtBearer()` + `AddAuthorization()`, validated against `Jwt:Issuer`/`Jwt:Audience`/`Jwt:SigningKey` — this is *our own* JWT, not Google's; Google is only consulted once, at login, via `IGoogleIdTokenValidator`), applies pending migrations on startup (`Database.MigrateAsync()` in a startup scope, before `app.Run()`), and registers global exception handling (`AddExceptionHandler<DomainExceptionHandler>()` + `AddProblemDetails()` + `app.UseExceptionHandler()`). Uses attribute-routed controllers (`AddControllers()` / `MapControllers()`), not minimal-API endpoints — all external call handlers live in `Controllers/`, calling into `MyApplication.Application` services/interfaces rather than containing business logic themselves; request/response DTOs live in `Models/` (distinct from the `Application` layer's own DTOs — map between them in the controller, e.g. `NotesController`, `AuthController`). `NotesController` is `[Authorize]`-protected and pulls the caller's id out of the JWT (`ClaimTypes.NameIdentifier`) rather than taking it as a request parameter.
  - `DomainExceptionHandler.cs` (namespace `MyApplication.Api`, root — not in `Controllers/`) — the single global exception handler: any `DomainException` (from Domain or Application) is mapped by a `switch` on its concrete type — `InvalidGoogleTokenException`/`InvalidRefreshTokenException` → 401, `NoteAccessDeniedException` → 403, `NoteConflictException` → 409, everything else (e.g. `NoteValidationException`, `NoteNotFoundException`) → 400 Bad Request — with the exception's message as the plain-text body. **Rule: controllers must not `catch` `DomainException`/`ApplicationException`/domain-specific exceptions themselves** — that mapping is centralized here on purpose, per explicit user instruction, so a controller action just calls the service and lets exceptions propagate. Adding a new exception type that needs a non-400 status means adding a case to this `switch`, not touching the exception type itself (no HTTP concept lives in Domain/Application). Anything that is *not* a `DomainException` is left unhandled by this handler and falls through to the generic `ProblemDetails` 500 response — verified live by stopping Postgres mid-request (a raw Npgsql connection failure, not a `DomainException`) and getting a 500. One consequence worth knowing: "not found" and "validation failed" are still not distinguishable by status code (both 400, unchanged) — only auth-related failures (401/403) and the version conflict (409) got their own codes.
  - Logging is configured in `Program.cs` via `Serilog` (`Serilog.AspNetCore`) + `Elastic.Serilog.Sinks`: writes to console and ships ECS-formatted logs directly to the Elasticsearch data stream `logs-myapplication-api-{environment}`. Elasticsearch endpoint comes from `Elasticsearch:Uri` (`appsettings.json`) / `Elasticsearch__Uri` env var.
  - Distributed tracing is configured in `Program.cs` via `OpenTelemetry.Extensions.Hosting` (`AddOpenTelemetry().WithTracing(...)`), with `AddAspNetCoreInstrumentation()` + `AddHttpClientInstrumentation()` + `AddNpgsql()` (from `Npgsql.OpenTelemetry`, covers every Postgres command executed through `NotesDbContext`) and an OTLP exporter. This propagates W3C `traceparent` across every incoming request and every outgoing `HttpClient`/Postgres call, and the trace/span IDs are auto-stamped onto Serilog/ECS log lines, so logs and traces correlate by `trace.id`. OTLP endpoint comes from `OpenTelemetry:OtlpEndpoint` (`appsettings.json`) / `OpenTelemetry__OtlpEndpoint` env var; if unset/unreachable, tracing is silently skipped.
  - **Rule: whenever a new outbound integration is added (a database client, a message queue producer/consumer, a call to another HTTP/gRPC service, etc.), add the matching OpenTelemetry instrumentation package for it in the same change** (e.g. Npgsql's native `Npgsql.OpenTelemetry`/`AddNpgsql()` or `OpenTelemetry.Instrumentation.EntityFrameworkCore` for Postgres/EF Core; the relevant instrumentation package for whatever message queue client is chosen), and register it in the `WithTracing(...)` call in `Program.cs`. Don't ship a new integration without tracing wired up — otherwise that hop becomes invisible in the trace.

  - Autosave (`notes/hooks/useNoteAutosave.ts`, used by `notes/components/NoteEditor.tsx`): a `draftRef` (not component state) holds the latest title/text so a save always reads fresh values regardless of which field fired last, avoiding stale-closure bugs. **Timing is "5s after the first unsaved change", not a debounce** (`docs/docs/notes/web-ui.md`): a plain `setTimeout` is started only by the first edit after a save and further keystrokes don't reset it (so continuous typing saves about every 5s), plus an immediate `flush()` on `onBlur` of the title/text fields, on `visibilitychange` → `hidden`, and on unmount. `savedRef` is a snapshot of what's on the server — a save is skipped if the draft equals it (blur without changes sends no request). Logout needs no explicit flush: opening the header's user menu already blurs the field, so the save is long in flight before "Выйти" is clicked. An empty/whitespace-only title is sent as `null` (`titleForRequest` in `notes/domain.ts`), and a note loaded with `title: null` becomes `""` in the draft — "no title" is real data (`Note.Title` is `string?`, stored as `NULL`, see the Domain entry below), not a UI-substituted string. `UNTITLED_TITLE` ("Без названия", `notes/domain.ts`) is display-only: the list (`NotesListPanel`, `Text c="dimmed"`), the view-mode heading (`NoteEditor`, dimmed `Title`) and the title input's placeholder show it, but it is never sent to the API or stored. `isUntitled` decides when to show it.
  - Conflict handling (same hook; `docs/docs/notes/web-ui.md`, "Заметка изменена в другом месте"): every `PUT` carries `versionRef`, which starts at `note.version` and is advanced from each save's *response* — so a chain of autosaves needs no re-read. A 409 (`ApiError.status`) sets `conflictRef`/`hasConflict`, which makes `requestSave` a no-op until resolved — without that the timer would re-send the same rejected request forever. The draft is deliberately left untouched, and `NoteEditor` renders a Mantine `Alert` with two buttons: "Загрузить актуальную" (`reloadFromServer` — `GET`s the note, replaces draft+`savedRef`+`versionRef` with it, invalidates the list) and "Перезаписать моей" (`overwriteWithMine` — `GET`s the note only to adopt its `version` and `savedRef`, then re-runs `requestSave`, so an identical server copy sends nothing at all). These two buttons are the one place with text labels rather than icon-only, since "download"/"upload" glyphs alone wouldn't say which side wins. Not solved here and worth knowing: an unresolved conflict at unmount loses the local draft, and a clean (non-dirty) editor still ignores a refetched `note`, so tab A keeps showing stale text until it conflicts — see the deliberate `key={note.id}` design above.
  - Save-status text (`notes/saveStatusText.ts`, pure function, covered by the exact wording rules in `docs/docs/notes/web-ui.md`): clamps `now - lastSavedAt` to a minimum of zero before formatting — `now` comes from a hook that only ticks every 30s (`useNow`), so right after a save completes it can briefly be a few seconds *behind* the just-updated `lastSavedAt`, which produced a real, observed `-1 минут назад` during manual testing before the clamp was added.
  - Search (`notes/components/NotesSearchBox.tsx` + `notes/hooks/useNotesSearch.ts`, spec in `docs/docs/notes/web-ui.md`, «Поиск»): a Mantine `Combobox` over a `TextInput` in `AppHeader`. Unlike autosave, this one **is** a debounce (`useDebouncedValue`, 300 ms) — a request per keystroke is pointless here. Below `MIN_SEARCH_QUERY_LENGTH` (3) the query is disabled *and the whole `Combobox.Dropdown` is not rendered* — `hidden` alone isn't enough, the markup stays in the DOM and a test (rightly) finds "Ничего не найдено" in it; `isActive` checks the *typed* text too, not just the debounced one, so erasing to two characters closes the list at once instead of after 300 ms. **Selection is two steps** (spec: `web-ui.md`, «Выбор результата»): a click or Enter on a row *previews* (`onPreview` = `useNoteSelection.select`; the note opens, dropdown/query/focus stay in the field), a repeated one on the row of the note that is already open (`id === openNoteId`, marked with a `Check` icon) *commits* — clears the field, closes the list, `onCommit` = `requestEditorFocus`. Enter with no highlighted row acts on the first result (Mantine's own Enter only handles an already-highlighted option, so `handleKeyDown` covers the `getSelectedOptionIndex() === -1` case). If the results for the *currently typed* text haven't arrived (`isSettled` false: debounce pending, or the screen still shows the previous text's results), that Enter is parked in `enterPending` and fires on the first row of the fresh results; any further typing cancels it — without this a fast typist's Enter opens a note from the previous query. Esc and the ✕ (`CloseButton`, `mousedown` prevented so it doesn't steal focus) both just clear the field, close the list and keep focus in it. **No results are kept between visits to the field:** `onFocus` calls `restart()`, which bumps `visit` in the query key (`notesKeys.search(query, visit)`); with `gcTime: 0`, and `placeholderData` keeping the previous results only when they belong to the *same* visit, smoothing between keystrokes stays but coming back to the field starts from «Идёт поиск…». A click on a row doesn't blur the input (`Combobox.Option` prevents the default `mousedown`), so previews don't start a new visit; a click elsewhere closes the dropdown (Popover click-outside) and keeps the query. Highlighting comes from the server as `{ text, match }` segments (`HighlightedText` renders `match` ones in Mantine's `<Mark>`); the client can't compute it itself, since a note found by a typo contains no literal occurrence of the query. A result with an empty `title` array is a note without a title → dimmed «Без названия», same as in the list.
  - `NotesListPanel`'s create button sends `title: null` (a new note has no title until the user types one).
  - `NoteEditor`'s title `TextInput` and text `Textarea` keep raw refs to their native `<input>`/`<textarea>` elements (`titleInputRef`/`textareaRef`) purely for `onKeyDown` cursor handoff — Enter or ArrowDown in the title moves focus into the text at position 0, and ArrowUp in the text while at position 0 moves focus back to the end of the title — so the title behaves like the document's first line rather than a separate field (per `docs/docs/notes/web-ui.md`, "Клавиатурная навигация между заголовком и текстом").

Gotchas already hit, don't rediscover:
    - **`vi.useFakeTimers()` hangs every `await user.…` unless `setup.ts` stubs a global `jest`** (`vi.stubGlobal("jest", { advanceTimersByTime })`): RTL's `asyncWrapper` waits on a faked `setTimeout(0)` and only advances fake clocks when it sees `jest`. Also fake only `setTimeout`/`clearTimeout`/`setInterval`/`clearInterval`/`Date` — leaving `setImmediate`/`nextTick` real — or MSW responses never resolve.
    - **Mantine's `Popover` dropdown (the search list) stays `display: none` forever in jsdom** — its transition never completes — so role queries can't see it and a closed one never leaves the DOM; `renderWithProviders` uses `MantineProvider env="test"` (Mantine's own switch: no transitions, inline portals) for that reason. Don't drop it to "match App.tsx" — text queries would keep working, which hides the problem until someone asserts absence or uses `getByRole`.
    - **`document.querySelector("textarea")` finds the wrong element**: the autosizing `Textarea` (react-textarea-autosize) leaves a hidden measuring `<textarea tabindex="-1">` in `body` that outlives the test. Use `textarea:not([tabindex='-1'])` (see `noteTextArea` in `NotesSearchBox.test.tsx`), and don't use `getByText` on text that's also in a note's `<textarea>` or view-mode markdown — scope it (`within(listbox)`).

    - TypeScript 7 doesn't auto-include `@types/node` (`tsconfig.app.json` sets no `types`), so app code can't use Node globals by accident; the one test helper that needs `setImmediate` (`src/test/advanceTime.ts`) opts in with `/// <reference types="node" />`.

    - When adding a test for a new behavior, check it actually fails without the behavior (mutate the production code, run, revert) — the autosave tests were verified this way (debounce instead of fixed timer, no `onBlur`, no unmount flush, no follow-up save, no dirty check, draft reset on `note` change each turn one or more of them red).

## Architecture role and rules

Role: You are an expert software architect specializing in Clean Architecture and Domain-Driven Design (DDD).

Strict Rules for Code Generation:
1. Architectural Layers: Always separate the codebase into distinct layers:
   - Domain (Enterprise business rules: Entities, Value Objects, Use Case Interfaces). Must have zero dependencies on other layers or external libraries.
   - Application (Application business rules: Use Case implementations, CQRS handlers, DTOs, Port interfaces for infrastructure).
   - Infrastructure (Frameworks, Database/ORM implementations, External APIs, Adapters).
   - Presentation (UI, Controllers, Presenters, API Endpoints).

2. Dependency Rule: Source code dependencies must only point inwards. Outer layers (Infrastructure/Presentation) can depend on inner layers (Application/Domain), but inner layers must NEVER depend on outer layers. Use Dependency Inversion (Interfaces) to achieve this.

3. Code Standards:
   - Write clean, maintainable, and heavily decoupled code.
   - Follow SOLID principles strictly.
   - Use meaningful names for classes and variables according to the domain.
   - Avoid mixing business logic with framework-specific code (e.g., no ORM annotations or HTTP status codes in the Domain layer).

Output Format:
- When asked to create a feature, explicitly structure your response by layers (Domain, Application, Infrastructure, Presentation).
- Provide the file paths and the exact code for each file.
- Explain briefly how the data flows between layers for the generated feature.
