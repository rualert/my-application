# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

The solution `src/MyApplication/MyApplication.sln` has five projects: `MyApplication.Domain`, `MyApplication.Application`, `MyApplication.Infrastructure`, `MyApplication.Api` (Presentation) — a full Clean Architecture layering — plus `MyApplication.Tests` (xUnit, not shipped). One use case exists: `Notes`, a real CRUD feature spanning all four layers, backed by PostgreSQL via EF Core. (An earlier `WeatherForecast` placeholder, inherited from the ASP.NET Core template, was deleted once it had no test coverage and no real business logic — don't recreate that pattern for new features.) A second Presentation surface, `src/MyApplication.Web.UI/` (React SPA), lives alongside the solution — a separate Node/npm project, not a `.sln` project — see its own entry in Structure below.

## Structure

- `README.md` — run instructions (local + Docker + Docker Compose/ELK + tracing + docs site).
- `docs/` — a separate [Docusaurus](https://docusaurus.io/) site documenting the application's **business logic** (use cases/business rules/API contracts), independent of this repo's technical README/CLAUDE.md. Content lives under `docs/docs/`, one folder per use case (currently just `notes/`, the CRUD notes feature), with `_category_.json` files controlling the sidebar tree — `sidebars.js` auto-generates the sidebar from that folder structure, so **adding a new use case is just adding a new folder** there. Has its own `package.json`/`node_modules`/`.npmrc` (Node/npm project, unrelated to the .NET solution) — `npm install --global=false && npm start` from `docs/`. `docs/.npmrc` forces local (non-global) installs — needed in some environments where a user-level npm config defaults `npm install` to global/misresolved locations; keep it even if your own environment doesn't need it. When real business logic is added to `MyApplication.Application`, add/update the corresponding page(s) under `docs/docs/` in the same change. **This also runs in reverse: treat `docs/docs/` as the spec.** If a change to `docs/docs/` describes new or different application behavior than what `MyApplication.Application` currently implements (not just wording/formatting edits), don't just accept the doc edit — point out the mismatch and propose the corresponding code change, and only implement it once the user confirms. Published automatically to GitHub Pages at `https://rualert.github.io/my-application/` by `.github/workflows/deploy-docs.yml` on every push to `master` touching `docs/**` — keep `docusaurus.config.js`'s `url`/`baseUrl` (`https://rualert.github.io` / `/my-application/`) in sync if the repo or org is ever renamed.
- `load-tests/` — [k6](https://k6.io/) load-test scenarios, plain JS, no `package.json`/build step, run via the `grafana/k6` Docker image or a local `k6` binary (not part of `MyApplication.Tests`, not restored/built by `dotnet`). One file per scenario under `scenarios/` (currently `notes-list.js` for `GET /Notes`, `notes-get-by-id.js` for `GET /Notes/{id}`, `notes-create.js` for `POST /Notes` — that one's own request load *is* the write being measured, `SEED_COUNT` there only sets the starting table size, not the thing under test), shared config in `config.js`, shared seeding helper in `lib/seed.js`. Each scenario uses the `ramping-arrival-rate` executor to step the target RPS up (stages configurable via `STAGE_TARGETS`/`STAGE_DURATION` env vars) against `thresholds` (`http_req_failed`, `http_req_duration` p99) — the goal is finding the highest RPS stage that still meets both, not a pass/fail CI gate. Points `BASE_URL` at a real deployed instance, not `WebApplicationFactory`, since in-process hosting doesn't reflect real network/connection-pool behavior under load — by default that's the isolated instance from `ci/docker-compose.load-tests-db.yml` (see below and the `scripts/` entry), not the regular dev app.
  - `lib/seed.js` — seeds `SEED_COUNT` notes via `http.batch()` in batches of `BATCH_SIZE` (50), not one request at a time. **A large `SEED_COUNT` (thousands) with sequential seeding blows past k6's default `setupTimeout` (60s)**, aborting the whole run with `setup() execution timed out` before any load is generated — looks from the outside like the `SEED_COUNT` parameter was silently ignored. Batching plus each scenario's `options.setupTimeout: '5m'` (defense-in-depth on top of batching) fixes that. If `SEED_COUNT` ever needs to go well beyond ~10k, re-check the batch math rather than assuming this is still headroom.
  - `lib/stageThresholds.js` — tags every request with its current stage's target RPS (`stage_rps`, computed from `k6/execution`'s `currentTestRunDuration` — k6 exposes no public API to ask the `ramping-arrival-rate` executor which stage it's on) and duplicates each scenario's `thresholds` as per-stage submetrics (`http_req_duration{stage_rps:400}`, etc), not just the whole-run aggregate.
  - `lib/maxRpsSummary.js` — each scenario's `handleSummary()` calls into this to scan those per-stage submetric thresholds and print `Maximum RPS satisfying thresholds: <n>` straight to the console (the highest stage where every threshold still passed) — no need to eyeball Grafana just to find that number. Defining `handleSummary()` stops k6's automatic summary print, so this reconstructs it via jslib's `textSummary` (fetched from `jslib.k6.io` at run time — needs outbound network from the k6 container/binary, same as any other remote k6 import). Also appends a markdown table row (date, max RPS, the scenario's `thresholds` rules, `SEED_COUNT`) to `results/<scenario>.md` — see below; `thresholds`/`SEED_COUNT` ride along because both can change between runs and the RPS number alone is meaningless without knowing which pair it was measured under. **Real k6 quirk, not a bug: `open()` only works during the init stage** (script top-level, before any iteration/VU runs) — calling it from inside `handleSummary()` itself throws `"open function is only available in the init stage"`, since by then the run has finished. That's why each scenario reads its results-file history (`readResultsHistory()`) at its own top level and only passes the already-read string into `summarizeMaxRps()`/`handleSummary()` — don't move that call into `handleSummary()` to "simplify" it, it'll break. Also note `open()` and the `handleSummary()` output-object keys resolve relative paths *differently*: `open()` is relative to the calling script file (`scenarios/`, hence the `../results/...` prefix used there), while output-object keys are relative to the k6 process's cwd (`load-tests/`, hence the bare `results/...` used for the written path) — confirmed empirically, not documented clearly by k6 itself.
  - `results/notes-list.md`, `results/notes-get-by-id.md`, `results/notes-create.md` — a markdown table (`| Дата | Max RPS | Thresholds | Seed count |`), one row per run, appended (not overwritten) by the `handleSummary()` mechanism above. A history in git, independent of InfluxDB/Grafana retention.
  - See `load-tests/README.md` for exact run commands. Results are also viewed in Grafana for the full time-series picture — see the `ci/docker-compose.load-tests.yml` entry below.
  - `scripts/` — PowerShell wrappers around the `docker run ... grafana/k6 run ...` invocation, for convenience on this (Windows) dev machine. `Invoke-K6Scenario.ps1` does the actual `docker run` (takes `-ScenarioFile`, `-AppPort`, `-BaseUrl`, `-Network`, `-InfluxUrl`, `-SeedCount`, `-StageDuration`, `-StageTargets`, `-KeepDb`); `Invoke-NotesListScenario.ps1`/`Invoke-NotesGetByIdScenario.ps1`/`Invoke-NotesCreateScenario.ps1` are thin per-scenario wrappers that forward `$PSBoundParameters` to it plus their own `-ScenarioFile`. A new scenario needs its own such wrapper (copy an existing one, swap the `-ScenarioFile` literal and the `.SYNOPSIS`/`.EXAMPLE` text — nothing else differs). Any new param added to `Invoke-K6Scenario.ps1` must be copy-pasted into every wrapper's own `param()` block too, or passing it to a wrapper fails with "parameter not found" — `$PSBoundParameters` only forwards what the *wrapper itself* declares. **Gotcha already hit once: declare RPS-list parameters as `[string[]]` (joined with `,` before use), not `[string]`** — PowerShell parses an unquoted comma-separated value like `-StageTargets 10,20` into an array at the call site before binding, so a `[string]` parameter fails to bind for that (very natural, unquoted) calling style. Also handles k6's exit code **99** specially — that means "a threshold was breached," the expected/normal outcome of these scenarios (not a tooling failure), so it's reported via `Write-Warning` instead of a terminating `throw`; any other non-zero code still throws. **`Invoke-K6Scenario.ps1` also owns the lifecycle of `ci/docker-compose.load-tests-db.yml`** (see below): brings it up before the k6 run, polls `http://localhost:$AppPort/Notes` from the host until it responds (no health endpoint/curl in the image for a Docker-level healthcheck, so this is done from PowerShell instead), then tears it down (`down -v`) in a `finally` block regardless of how the k6 run went — unless `-KeepDb` is passed. Default `-BaseUrl` points at this isolated instance (`http://host.docker.internal:$AppPort`, `$AppPort` defaults to 8081), not the regular dev app on 8080.
- `.github/workflows/deploy-docs.yml` — builds `docs/` (`npm ci && npm run build`) and deploys `docs/build` to GitHub Pages via `actions/deploy-pages`. Triggers on push to `master` (paths `docs/**`) or manually (`workflow_dispatch`). Requires the repo's **Settings → Pages → Source** to be set to "GitHub Actions" (one-time, done outside the workflow itself).
- `.github/workflows/tests.yml` — `dotnet restore` / `build` / `test` (`MyApplication.Tests`, all 27 tests including `SmokeTests`) on every PR targeting `master`. Not `load-tests/` (separate JS tooling, never runs in CI — see `load-tests/README.md`). `ubuntu-latest` already has Docker running, so `SmokeTests`' Testcontainers-based Postgres needs no extra setup step. To make this a required check (block merging on failure), enable it under the repo's **Settings → Branches → Branch protection rules** — the workflow file alone doesn't enforce that.
- `ci/` — every Dockerfile / Docker Compose file lives here (moved out of the repo root once there were enough of them to be clutter — explicit user request). All commands below are run **from the repo root**, not from inside `ci/` (`docker compose -f ci/docker-compose.X.yml ...`, `docker build -f ci/Dockerfile ...`) — this matters because compose resolves a file's relative paths (bind mounts, build context) against the compose file's own directory, and the Dockerfile's `COPY` paths are relative to the build context, not the Dockerfile's location; moving these files changed those resolutions, not just their address:
  - `Dockerfile` — multi-stage build (SDK → aspnet runtime) for `MyApplication.Api`, listens on port 8080 in the container. Restore is scoped to `dotnet restore .../MyApplication.Api.csproj` (not the whole `.sln`), so it only needs `.csproj` files for projects `MyApplication.Api` actually references — currently Api, Application, Infrastructure, Domain. Add a new `COPY ... .csproj` line here whenever a new project is added to *that* dependency graph; `MyApplication.Tests` (and any other project the shipped API doesn't reference) deliberately doesn't need one. Every compose file that builds this image sets `context: ..` (repo root — `COPY` paths inside the Dockerfile are written as `src/MyApplication/...`) and `dockerfile: ci/Dockerfile`, since context and Dockerfile location are two independent settings.
  - `Dockerfile.web-ui` — multi-stage build (`node:22-alpine` → `nginx:1.27-alpine`) for `MyApplication.Web.UI`: builds the Vite app (`npm ci --global=false && npm run build`), then copies `dist/` into an nginx image alongside `nginx.conf`. Same `context: ..` / `dockerfile: ci/Dockerfile.web-ui` convention as the API's `Dockerfile`. **Root `.dockerignore` excludes `**/node_modules/` and `**/dist/`** — without that, `COPY src/MyApplication.Web.UI/ ./` after `npm ci` would overwrite the container's freshly-installed Linux `node_modules` with the host's own (Windows) one, breaking native binary shims like `tsc` (`node.exe: not found` at build time) — hit and fixed once, don't drop that ignore rule.
  - `nginx.conf` — serves the built UI's static files and reverse-proxies `/Notes` to `http://myapplication-api:8080` (the API's service/container name inside the `elastic` network) — same origin for the browser, so no CORS setup needed. If a new API route prefix is ever added that the UI calls, add a matching `location` block here.
  - `.dockerignore` — **deliberately stayed at the repo root, not moved into `ci/`**, unlike everything else here. Docker looks for it at the build *context* root (repo root, since `context: ..`), not next to the Dockerfile — moving it into `ci/` would silently stop it from being applied (no error, just a bigger/dirtier build context).
  - The app and its supporting services deploy as three **independent** Compose stacks, joined only by a shared external Docker network `elastic` (declared with `external: true` in the app/db stacks) — never merge them back into one file. `docker-compose.elk.yml` is the one that creates the network, so it must be started at least once before the other two:
    - `docker-compose.elk.yml` — single-node Elasticsearch + Kibana + APM Server (security disabled, dev-only). Owns/creates the `elastic` network. APM Server receives OTLP traces on `:8200` (gRPC and HTTP multiplexed on the same port) and writes them to Elasticsearch `traces-apm-*`, visible in Kibana under Observability → APM.
    - `docker-compose.db.yml` — single PostgreSQL instance (`postgres:17`), db/user/password all `myapplication`, port 5432. Just infra — no app-specific init scripts; the app applies EF Core migrations itself.
    - `docker-compose.app.yml` — `myapplication-api` plus `myapplication-web-ui` (nginx serving `MyApplication.Web.UI`, port 80, built from `ci/Dockerfile.web-ui`; depends on `myapplication-api` and shares the `elastic` network so nginx can resolve it by service name — see `nginx.conf` above). The API requires the `elastic` network (from the ELK stack) and, unlike the logging/tracing endpoints which degrade gracefully, requires `postgres` (from the db stack) to already be reachable — the app calls `Database.MigrateAsync()` on startup and will fail to start otherwise.
  - `docker-compose.load-tests.yml` — the standard k6 results stack: InfluxDB (metrics store, k6 writes to it via `--out influxdb=http://influxdb:8086/k6`) + Grafana (`localhost:3000`, anonymous Admin access — local-only tooling, never exposed). Fully self-contained/independent of the app's own `elk`/`db`/`app` stacks — k6 just needs network access to both this stack (to write results) and the running app (to generate load), so it's run with `--network myapplication_default` (the network this compose file creates) plus `BASE_URL` pointing at the host-published app port (the isolated load-test instance by default — see `docker-compose.load-tests-db.yml` below). Has an explicit top-level `name: myapplication` — without it, Docker Compose would derive the project (and thus default network) name from this file's own directory (`ci`) instead of the repo root, silently renaming the network to `ci_default` and breaking every hardcoded `--network myapplication_default` reference (`load-tests/scripts/Invoke-K6Scenario.ps1`'s default, the docs). Grafana auto-provisions on first start from `../load-tests/grafana/provisioning/` (InfluxDB datasource named `InfluxDB-k6`) and `../load-tests/grafana/dashboards/k6-load-testing-results.json` (the classic community "k6 Load Testing Results" dashboard, grafana.com id 2587 — downloaded once and hand-edited to replace its `${DS_K6}` template-variable datasource references with the literal `InfluxDB-k6` name, since file-based dashboard provisioning doesn't resolve those import-wizard template variables the way Grafana's UI import does). If that dashboard JSON is ever re-fetched/regenerated, redo that substitution or the panels will show "datasource not found".
  - `docker-compose.load-tests-db.yml` — a disposable, fully isolated Postgres + API instance (`postgres-loadtest` on host port 5433, `myapplication-api-loadtest` on host port 8081) used only while a k6 scenario is running, so `SEED_COUNT` (thousands of notes) never pollutes the real dev database (`docker-compose.db.yml`). No `elastic` network, no logging/tracing env vars — deliberately self-contained, unlike `docker-compose.app.yml`. `load-tests/scripts/Invoke-K6Scenario.ps1` manages its whole lifecycle automatically (see the `load-tests/` → `scripts/` entry above) via `docker compose -p myapplication-loadtest -f ci/docker-compose.load-tests-db.yml up -d --build` / `... down -v` — the explicit `-p myapplication-loadtest` keeps it in its own Docker network/namespace rather than sharing `myapplication_default` with the other stacks (so it doesn't need the `name:` trick `docker-compose.load-tests.yml` needs above). `down -v` matters: without `-v` the named volume (`postgres-loadtest-data`) would survive and the next run wouldn't start from an empty database. Manual up/down commands for debugging are in the file's own header comment.
- `src/MyApplication/MyApplication.sln` — the solution file.
- `src/MyApplication/MyApplication.Domain/` — Domain layer class library. Zero dependency on any other project or framework/web package (not even EF Core — no ORM annotations here per the Dependency Rule). Organized in feature folders (e.g. `Notes/`): entities enforce their own invariants through private setters + factory/mutator methods that validate and throw a domain-specific exception (e.g. `Note.Create`/`Note.Update` throwing `NoteValidationException`), never plain public setters.
  - `DomainException.cs` (namespace `MyApplication.Domain`, no feature subfolder) — abstract base class for **every** exception that should be treated as a client error (400) by the API, across both this layer and `MyApplication.Application`. **Rule: a business-rule/invariant violation raised directly from `MyApplication.Domain` must derive from `DomainException`** (e.g. `NoteValidationException : DomainException`). See `MyApplication.Api/DomainExceptionHandler.cs` for how this gets mapped to a response.
- `src/MyApplication/MyApplication.Api/` — ASP.NET Core Web API project (Presentation layer). Entry point: `Program.cs`, which wires up DI (registering `Application` layer services and their `Infrastructure` implementations — this is the only place allowed to reference `MyApplication.Infrastructure` directly), Serilog, OpenTelemetry tracing, EF Core (`AddDbContext`), applies pending migrations on startup (`Database.MigrateAsync()` in a startup scope, before `app.Run()`), and registers global exception handling (`AddExceptionHandler<DomainExceptionHandler>()` + `AddProblemDetails()` + `app.UseExceptionHandler()`). Uses attribute-routed controllers (`AddControllers()` / `MapControllers()`), not minimal-API endpoints — all external call handlers live in `Controllers/`, calling into `MyApplication.Application` services/interfaces rather than containing business logic themselves; request/response DTOs live in `Models/` (distinct from the `Application` layer's own DTOs — map between them in the controller, e.g. `NotesController`).
  - `DomainExceptionHandler.cs` (namespace `MyApplication.Api`, root — not in `Controllers/`) — the single global exception handler: any `DomainException` (from Domain or Application, e.g. `NoteValidationException`, `NoteNotFoundException`) → 400 Bad Request with the exception's message as the plain-text body. **Rule: controllers must not `catch` `DomainException`/`ApplicationException`/domain-specific exceptions themselves** — that mapping is centralized here on purpose, per explicit user instruction, so a controller action just calls the service and lets exceptions propagate. Anything that is *not* a `DomainException` is left unhandled by this handler and falls through to the generic `ProblemDetails` 500 response — verified live by stopping Postgres mid-request (a raw Npgsql connection failure, not a `DomainException`) and getting a 500. One consequence worth knowing: "not found" and "validation failed" are no longer distinguishable by status code (both are 400) — only by the message text in the body.
  - Logging is configured in `Program.cs` via `Serilog` (`Serilog.AspNetCore`) + `Elastic.Serilog.Sinks`: writes to console and ships ECS-formatted logs directly to the Elasticsearch data stream `logs-myapplication-api-{environment}`. Elasticsearch endpoint comes from `Elasticsearch:Uri` (`appsettings.json`) / `Elasticsearch__Uri` env var.
  - Distributed tracing is configured in `Program.cs` via `OpenTelemetry.Extensions.Hosting` (`AddOpenTelemetry().WithTracing(...)`), with `AddAspNetCoreInstrumentation()` + `AddHttpClientInstrumentation()` + `AddNpgsql()` (from `Npgsql.OpenTelemetry`, covers every Postgres command executed through `NotesDbContext`) and an OTLP exporter. This propagates W3C `traceparent` across every incoming request and every outgoing `HttpClient`/Postgres call, and the trace/span IDs are auto-stamped onto Serilog/ECS log lines, so logs and traces correlate by `trace.id`. OTLP endpoint comes from `OpenTelemetry:OtlpEndpoint` (`appsettings.json`) / `OpenTelemetry__OtlpEndpoint` env var; if unset/unreachable, tracing is silently skipped.
  - **Rule: whenever a new outbound integration is added (a database client, a message queue producer/consumer, a call to another HTTP/gRPC service, etc.), add the matching OpenTelemetry instrumentation package for it in the same change** (e.g. Npgsql's native `Npgsql.OpenTelemetry`/`AddNpgsql()` or `OpenTelemetry.Instrumentation.EntityFrameworkCore` for Postgres/EF Core; the relevant instrumentation package for whatever message queue client is chosen), and register it in the `WithTracing(...)` call in `Program.cs`. Don't ship a new integration without tracing wired up — otherwise that hop becomes invisible in the trace.
  - Postgres connection string: `ConnectionStrings:Notes` (`appsettings.json`) / `ConnectionStrings__Notes` env var. Unlike logging/tracing, this one is a hard requirement — the app fails to start if Postgres isn't reachable (migrations).
  - API docs: `AddOpenApi()`/`MapOpenApi()` (built-in `Microsoft.AspNetCore.OpenApi`, no Swashbuckle) serves the raw spec at `/openapi/v1.json`; `Scalar.AspNetCore`'s `MapScalarApiReference()` serves an interactive UI at `/scalar` on top of it. Both are mapped only inside `if (app.Environment.IsDevelopment())` — not available when `ASPNETCORE_ENVIRONMENT=Production` (i.e. not in the Docker Compose/plain-`docker` deployments as currently configured).
- `src/MyApplication/MyApplication.Application/` — Application layer class library. Zero dependency on `MyApplication.Api`, `MyApplication.Infrastructure`, or any framework/web package (does depend on `MyApplication.Domain`). Organized in feature folders (e.g. `Notes/`), each holding its DTOs (e.g. `NoteSummary.cs`/`NoteDetails.cs` — distinct from `MyApplication.Api/Models/` and from the `MyApplication.Domain` entity), a port interface for anything Infrastructure needs to implement (e.g. `INoteRepository.cs`), an application-level exception for use-case-level failures like "not found" (e.g. `NoteNotFoundException.cs` — as opposed to entity-invariant failures, which are `MyApplication.Domain` exceptions), and the use-case implementation (e.g. `NoteService.cs` implementing `INoteService`). Register new services in `MyApplication.Api/Program.cs`'s DI container.
  - `ApplicationException.cs` (namespace `MyApplication.Application`, no feature subfolder) — abstract base class for **every** exception thrown from this layer, itself deriving from `MyApplication.Domain.DomainException` (so it's covered by the same global 400 handler — see the `MyApplication.Api` entry below). **Rule: every new Application-layer exception must derive from `MyApplication.Application.ApplicationException`, not directly from `Exception`** (e.g. `NoteNotFoundException : ApplicationException`). This is a project-local type, unrelated to `System.ApplicationException` from the BCL — the two share a name and resolve differently depending on context (our type wins via enclosing-namespace lookup for code inside `MyApplication.Application.*`, without needing a `using`), which is intentional per an explicit user request but worth remembering when reading/writing code here.
- `src/MyApplication/MyApplication.Infrastructure/` — Infrastructure layer class library. Depends on `MyApplication.Application` (implements its port interfaces) and `MyApplication.Domain`, plus whatever external/framework packages a given integration needs; never depends on `MyApplication.Api`. Organized in feature folders mirroring the `Application` port they implement, e.g. `Notes/`: `NotesDbContext` (EF Core `DbContext`, entity mapping in `OnModelCreating` — no attributes on the `Domain` entity itself) + `NoteRepository` (implements `INoteRepository`) + `Notes/Migrations/` (EF Core migrations, see the `dotnet ef migrations add` command in `README.md`). Remember the tracing rule above whenever a new integration is added here.
  - `Npgsql.EntityFrameworkCore.PostgreSQL` here and `Microsoft.EntityFrameworkCore.Design` in `MyApplication.Api` **must stay on matching EF Core versions** (currently both effectively on EF Core 10.0.4) — a mismatch produces an MSB3277 assembly-version-conflict warning at build time (harmless at runtime, but a smell) and can make `dotnet ef` misbehave. When bumping one, bump the other to match.
- `src/MyApplication/MyApplication.Tests/` — xUnit test project (`MyApplication.Tests.csproj`, not published/shipped — `ci/Dockerfile`'s restore graph deliberately excludes it, see above). References all four layers (`Domain`, `Application`, `Infrastructure`, `Api`) so tests can reach into any of them. **Organize by test kind, one top-level folder per kind.** Style rules across every test kind (explicit user instruction):
  - Helper/infrastructure classes (fixtures, base classes, collection definitions — anything without `[Fact]`/`[Theory]` methods) go in a `Harness/` subfolder of whichever folder they support (e.g. `UseCasesTests/Notes/Harness/`, `SmokeTests/Harness/`), namespace suffixed `.Harness` to match. Actual test classes stay directly in their feature folder.
  - The property/variable holding the system under test is always named `Sut` (e.g. `NoteServiceTestBase.Sut` is `INoteService`; `SmokeTestFixture.Sut`/`SmokeTestBase.Sut` is the `HttpClient`).
  - Every test method's body is split into `// Arrange`, `// Act`, `// Assert` comments, in that order, even when a section has no statements (e.g. a test with no setup still gets an empty `// Arrange` immediately followed by `// Act`).
  - `ArchitectureTests/` is exempt from all three of the above for now — see the permission rule right below; ask before applying this styling there too.

  Current kinds:
  - `ArchitectureTests/` — solution-wide structural rules (reflection-based, no `NetArchTest`/`ArchUnitNET` dependency pulled in yet — added only if a rule genuinely needs it). **Rule: never modify a file under `ArchitectureTests/` without the user's explicit permission first** — ask before editing, even to "fix" a failure; the correct response to a failing architecture test is normally to fix the production code so it satisfies the rule, not to loosen the test (explicit user instruction).
    - `ExceptionHierarchyTests.cs` — asserts every declared `Exception`-derived type is (or inherits) `MyApplication.Domain.DomainException`. Enforces the rule already stated above under `DomainException.cs`/`ApplicationException.cs`; keep this test in sync if that base-class scheme ever changes (with the user's permission — see the rule above). The set of assemblies to scan isn't hardcoded — `GetSolutionAssemblies()` walks the reference graph starting from `MyApplication.Api` (loaded by name) and follows any referenced assembly whose name starts with `MyApplication.`, so a new project is picked up automatically the moment `MyApplication.Api` starts depending on it (directly or transitively); nothing to update here when that happens.
  - `UseCasesTests/` — one subfolder per major feature (e.g. `Notes/`), one file per use case/scenario within it (e.g. `CreateNoteTests.cs`, `GetNoteByIdTests.cs`, `ListNotesTests.cs`, `UpdateNoteTests.cs`, `DeleteNoteTests.cs` under `Notes/`). Tests the `Application` layer service (e.g. `NoteService`) as a **black box**, only through its public interface (`INoteService`) — assert against documented behavior (the `docs/docs/<feature>/` pages, the interface's own XML docs, and the public exception types), never against `NoteService`'s internal implementation details.
    - **Rule: never fake/mock the `Application` layer's port interface (e.g. `INoteRepository`) for these tests** — explicit user instruction, because a hand-rolled fake silently bypasses whatever logic the real `Infrastructure` implementation has (now or in the future) and gives false confidence. Instead, wire the **real** `Infrastructure` repository (e.g. `NoteRepository`) against a real `DbContext` (e.g. `NotesDbContext`), and only swap the database underneath it. Per-feature shared setup for this lives in a base class (e.g. `Notes/Harness/NoteServiceTestBase.cs`) that each scenario file inherits from.
    - Database substitute: **EF Core's InMemory provider** (`Microsoft.EntityFrameworkCore.InMemory`, test project only), one uniquely-named in-memory database per test instance (`UseInMemoryDatabase(Guid.NewGuid().ToString())`). This was a deliberate, discussed choice, not a default: a real SQLite in-memory database was tried first (closer to relational reality), but hit a genuine SQLite/EF Core provider limitation — SQLite can't translate `ORDER BY` on a `DateTimeOffset` column (`NoteRepository.GetAllAsync()`'s `OrderByDescending(note => note.CreatedAt)`), unrelated to any bug in this codebase. Rather than special-case the production `NotesDbContext` model just to appease SQLite, the user chose the InMemory provider instead, accepting its known trade-off (Microsoft's own docs: it's not a relational database and shouldn't be trusted for relational-behavior fidelity) in exchange for simplicity. If a future infra change needs closer-to-Postgres fidelity than InMemory gives (e.g. testing a raw SQL query, a constraint, a transaction), that trade-off should be revisited with the user rather than silently worked around.
  - `SmokeTests/` — one file per major feature (e.g. `NotesSmokeTests.cs`), containing **only blue-sky (happy-path) scenarios, one per operation** — no error/edge cases, those belong in `UseCasesTests/`. Tests **the whole running service** as a black box: real HTTP calls (`HttpClient`) against the app hosted in-process via `Microsoft.AspNetCore.Mvc.Testing`'s `WebApplicationFactory<Program>` — the full ASP.NET Core pipeline, real `NoteRepository`/`NotesDbContext`, no swapped components at all except the database. (`MyApplication.Api/Program.cs` has a trailing `public partial class Program { }` specifically so `WebApplicationFactory<Program>` can reference it — top-level-statement programs otherwise generate an inaccessible `Program` class.)
    - Database: a **real PostgreSQL** via `Testcontainers.PostgreSql`, **one container per test session** (not per test) — shared through an xUnit `ICollectionFixture<SmokeTestFixture>` (`SmokeTestCollection.cs`, `[Collection(SmokeTestCollection.Name)]` on every smoke test class via `SmokeTestBase`). The app applies its own EF Core migrations against that container on startup (same `Database.MigrateAsync()` call as production, nothing test-specific). This is a different trade-off than `UseCasesTests`' InMemory provider on purpose — smoke tests exist specifically to validate the real deployable service end-to-end, so full Postgres fidelity matters more here than fast/isolated unit-style runs.
    - Cleanup between scenarios: **Respawn** (`Respawner.CreateAsync`/`ResetAsync`, `DbAdapter.Postgres`), built once against the started container and invoked before each test via `SmokeTestBase.InitializeAsync()`. Chosen specifically so nobody has to hand-maintain per-table `DELETE`/`TRUNCATE` scripts — Respawn introspects the schema itself, so a new table is picked up automatically.
    - Local/CI environment note: if the Docker daemon's API version is older than what `Testcontainers`' `Docker.DotNet` dependency requests by default, container creation fails with `"client version X.XX is too new"`. `TestcontainersCompatibility.cs` works around this with a `[ModuleInitializer]` that pins `DOCKER_API_VERSION=1.41` unless it's already set — don't remove this without checking whether it's still needed (i.e. Docker Desktop got updated) or would break a CI environment that sets its own value.
- `src/MyApplication.Web.UI/` — React + TypeScript SPA (Presentation layer for the `Notes` use case), a sibling of `src/MyApplication/`, not part of the `.sln` — its own Node/npm project (`package.json`/`node_modules`/`.npmrc`, like `docs/`), scaffolded by hand (not `create-vite`, see below) with Vite as the build tool. Requirements for this UI live in `docs/docs/notes/web-ui.md` — treat that doc as the spec here too, same rule as for `MyApplication.Application` above. `npm install --global=false` (this machine's npm defaults to a global install otherwise — see `.npmrc`), `npm run dev` (dev server on `:5173`, proxies `/Notes` to `http://localhost:5184` per `vite.config.ts` — matches the API's local `dotnet run` port, not the Docker one), `npm run build` (`tsc -b && vite build`, output to `dist/`). Stack: **Mantine** (`@mantine/core`/`@mantine/hooks`) for components/layout/the autosave debounce hook, **TanStack Query** (`@tanstack/react-query`) for server state (`useInfiniteQuery` for the notes list, mutations for create/update/delete with cache patching instead of full invalidation), **react-markdown** for the read-only view mode, **lucide-react** for icons (every button is icon-only per the design spec). Organized by feature, mirroring the backend: `api/` (fetch client + DTOs matching `MyApplication.Api/Models` — System.Text.Json's default camelCase), `notes/hooks/` (one hook per query/mutation, plus `useNoteAutosave` and `useNow`), `notes/components/` (`NotesApp` = layout/selection state, `NotesListPanel` = collapsible list + infinite scroll + create/delete, `NoteEditorPanel` = edit/view toggle + autosave + save-status text).
  - `npx`/`npm create vite@...` don't work reliably on this machine (see the npm-global-install issue referenced above — `npx`'s own cache path can 404) — the project was scaffolded file-by-file instead (`package.json`, `tsconfig*.json`, `vite.config.ts`, `index.html`, `src/`) and dependencies added via plain `npm install --global=false <pkg>`, letting npm resolve/pin versions in `package.json`/`package-lock.json` rather than guessing version numbers by hand.
  - Same-origin API access, no CORS: in dev, `vite.config.ts`'s `server.proxy` forwards `/Notes` to the API; in Docker, `ci/nginx.conf` does the same via `location /Notes { proxy_pass ... }` (see the `ci/` entry above). Never hardcode a different-origin API base URL here.
  - Autosave (`notes/hooks/useNoteAutosave.ts`): a `draftRef` (not component state) holds the latest title/text so the debounced save (Mantine's `useDebouncedCallback`, 5s) always reads fresh values regardless of which field fired last, avoiding stale-closure bugs. An empty/whitespace-only title is replaced with `UNTITLED_TITLE` ("Без заголовка", `notes/domain.ts`) before saving — the Domain layer's `Note` requires a non-blank title, so the UI, not the API, is responsible for supplying the fallback.
  - Save-status text (`notes/saveStatusText.ts`, pure function, covered by the exact wording rules in `docs/docs/notes/web-ui.md`): clamps `now - lastSavedAt` to a minimum of zero before formatting — `now` comes from a hook that only ticks every 30s (`useNow`), so right after a save completes it can briefly be a few seconds *behind* the just-updated `lastSavedAt`, which produced a real, observed `-1 минут назад` during manual testing before the clamp was added.
  - `NotesListPanel`'s create button always sends `title: UNTITLED_TITLE` (never an empty string) for the same Domain-validation reason as autosave above.
  - `NoteEditorPanel`'s title `TextInput` and text `Textarea` keep raw refs to their native `<input>`/`<textarea>` elements (`titleInputRef`/`textareaRef`) purely for `onKeyDown` cursor handoff — Enter or ArrowDown in the title moves focus into the text at position 0, and ArrowUp in the text while at position 0 moves focus back to the end of the title — so the title behaves like the document's first line rather than a separate field (per `docs/docs/notes/web-ui.md`, "Клавиатурная навигация между заголовком и текстом").

## Architecture role and rules

Role: You are an expert software architect specializing in Clean Architecture and Domain-Driven Design (DDD).

Strict Rules for Code Generation:
1. Architectural Layers: Always separate the codebase into distinct layers:
   - Domain (Enterprise business rules: Entities, Value Objects, Use Case Interfaces). Must have zero dependencies on other layers or external libraries.
   - Application (Application business rules: Use Case implementations, CQRS handlers, DTOs, Port interfaces for infrastructure).
   - Infrastructure (Frameworks, Database/ORM implementations, External APIs, Adapters).
   - Presentation (UI, Controllers, Presenters, API Endpoints).

2. Dependency Rule: Source code dependencies must only point inwards. Outer layers (Infrastructure/Presentation) can depend on inner layers (Application/Domain), but inner layers must NEVER depend on outer layers. Use Dependency Inversion (Interfaces) to achieve this.

3. Code Standards:
   - Write clean, maintainable, and heavily decoupled code.
   - Follow SOLID principles strictly.
   - Use meaningful names for classes and variables according to the domain.
   - Avoid mixing business logic with framework-specific code (e.g., no ORM annotations or HTTP status codes in the Domain layer).

Output Format:
- When asked to create a feature, explicitly structure your response by layers (Domain, Application, Infrastructure, Presentation).
- Provide the file paths and the exact code for each file.
- Explain briefly how the data flows between layers for the generated feature.
