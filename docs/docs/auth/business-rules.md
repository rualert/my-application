# Правила выдачи и жизни токенов

Реализовано в `AuthService` (`src/MyApplication/MyApplication.Application/Auth/AuthService.cs`).

## Пользователь

Создаётся при первом входе через Google, идентифицируется по
`GoogleSubjectId` (идентификатор профиля Google — не email, чтобы смена
email в Google-аккаунте не создавала второго пользователя). При каждом
повторном входе email и имя обновляются свежими данными из профиля Google.

## Приветственная заметка

При **первом** входе (то есть при создании пользователя) ему заводится одна
приветственная заметка:

- заголовок — «Добро пожаловать»;
- текст (Markdown) — приветствие, цель проекта, ссылка на репозиторий на
  GitHub, краткое описание возможностей приложения и — **в самом конце** —
  список горячих клавиш (раздел «Горячие клавиши»: двойной Shift для поиска,
  клавиши поиска, переходы между заголовком и текстом);
- это обычная заметка пользователя (см. [«Заметки»](/notes/overview)): её
  можно изменить или удалить.

Повторные входы её не создают — в том числе если пользователь свою заметку
удалил: заново она не появится. Существующие пользователи, зарегистрированные
до появления этого правила, приветственную заметку не получают.

Реализовано через порт `IUserRegistrationHandler` (`Application/Auth`):
`AuthService` вызывает его для нового пользователя, а реализация
`WelcomeNoteRegistrationHandler` живёт в фиче «Заметки» — Auth сам про заметки
ничего не знает.

### Регистрация и заметка не атомарны — это осознанное решение

Пользователь и его приветственная заметка сохраняются **раздельно**: сначала
пользователь (`AuthDbContext`), затем заметка (`NotesDbContext`), общей
транзакции между ними нет. Если создание заметки завершится ошибкой, вход
вернёт ошибку (`500`), но пользователь уже будет создан — при следующем входе
он найдётся как существующий, и приветственная заметка у него не появится.
То есть правило «у нового пользователя есть приветственная заметка» **не
гарантируется**.

Почему с этим мирятся:

- Auth и Notes — независимые bounded context'ы с собственными `DbContext`, и
  общая транзакция слила бы их в одну единицу работы. То, что сейчас обе
  фичи используют одну физическую базу, — деталь развёртывания.
- Приветствие вспомогательное: его отсутствие ничему не мешает, а любой
  механизм гарантии стоит дороже самой заметки.
- Сбой возможен практически лишь при недоступной базе — но тогда не удался
  бы и следующий шаг входа (сохранение refresh token).

Если гарантия когда-нибудь понадобится, правильный путь — transactional
outbox (запись «пользователь зарегистрирован» сохраняется вместе с самим
пользователем, а потребитель идемпотентно создаёт заметку), а не общая
транзакция. То же обоснование записано в комментарии в
`AuthService.LoginWithGoogleAsync`.

## Access token

- JWT, подписанный сервером (HMAC-SHA256, ключ — конфигурация
  `Jwt:SigningKey`, не Google).
- Срок действия — 15 минут по умолчанию (`Jwt:AccessTokenLifetimeMinutes`).
- Передаётся клиентом в заголовке `Authorization: Bearer <token>`.
- Содержит идентификатор пользователя (`sub`), email и имя.

## Refresh token

- Случайная строка (не JWT), хранится на сервере в виде SHA-256 хэша — сырое
  значение нигде, кроме момента выдачи клиенту, не сохраняется.
- Срок действия — 30 дней.
- Веб-клиент хранит его в httpOnly/Secure/SameSite=Strict cookie, скоуп —
  только на `/Auth` (см. [контракт API](./api-contract)); недоступен
  клиентскому JS.
- **Ротация**: каждый `POST /Auth/refresh` отзывает использованный refresh
  token и выдаёт новый — повторное использование уже отозванного токена
  считается невалидным (`InvalidRefreshTokenException`, 401).
- У одного пользователя может быть несколько одновременно активных refresh
  token'ов (по одному на сессию/устройство) — они хранятся как отдельные
  записи, а не единым полем на пользователе, специально ради поддержки
  нескольких параллельных клиентов (веб, в будущем — мобильный).

## Нарушение правил

- Невалидный/просроченный/выданный не для этого приложения Google ID token
  → `InvalidGoogleTokenException` → `401`.
- Отсутствующий/просроченный/уже отозванный refresh token → `InvalidRefreshTokenException` → `401`.
- Отсутствующий/невалидный access token на защищённом эндпоинте (например,
  `/Notes`) → `401` (проверяется JWT bearer middleware ещё до контроллера).
- Валидный access token, но обращение к чужому ресурсу (например, к чужой
  заметке) → `403`, см. [«Заметки»](/notes/overview).
